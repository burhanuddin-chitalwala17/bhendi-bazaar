# CLAUDE.md — checkout domain

- **Verified:** 2026-11-01
- **Covers:** `server/checkout/**`

> **Read the project-wide rules first:** [`/CLAUDE.md`](../../CLAUDE.md) covers the SDLC and the seven Project Invariants. This file covers **checkout** only.

## Purpose
Checkout owns an order's existence and lifecycle — placement, state transitions, and lookup. It is the orchestrating domain: it reads prices from `catalog`, reserves stock there, asks `payments` to collect money, and hands `shipping` something to send. It calls no external service itself.

## Boundaries

**Owns:** `server/checkout/**` — `order.service.ts`, `order.repository.ts`, `order.types.ts`, the three collaborators described under *Structure*, and the `admin.order.*` reads that power the admin console.

**Does not own:** what an item costs (`catalog`), whether money arrived (`payments`), or whether a parcel exists (`shipping`). It composes them.

## Rules

- **The server computes every monetary field** from persisted catalogue data. A price or total arriving in a request body is discarded, not validated ([ADR-0002](../../docs/adr/0002-server-holds-pricing-authority.md), [server-side-pricing-authority](../../docs/specs/server-side-pricing-authority/)).
- **Never write `paymentStatus`.** That belongs to `payments`, which has exactly one writer ([ADR-0005](../../docs/adr/0005-payment-state-server-only.md)).
- **Order creation, stock reservation, and removing the bought lines from the cart are one transaction.** Only the bought lines — a Buy Now or a mid-checkout sign-in leaves the rest of the cart alone, and the cart is reached through `cartService.removeBoughtLinesIn`, never `tx.cart` ([seamless-sign-in](../../docs/specs/seamless-sign-in/) D12). An order must not exist without its stock movement ([inventory-reservation](../../docs/specs/inventory-reservation/)).
- **An ownership check is not `if (userId && ...)`.** A guard that skips when the identity is absent is not a guard — an anonymous caller passes it. Check identity presence and ownership as separate conditions, and decide explicitly what a guest order permits.
- **An abandoned checkout is kept and hidden, never deleted.** `status: "expired"` is the marker, and `VISIBLE_ORDER_WHERE` is applied inside the repositories — a new order query that does not carry it will show abandoned checkouts as business ([checkout-abandonment](../../docs/specs/checkout-abandonment/)).
- **`Order.status` and `Order.paymentStatus` values come from `ORDER_STATUS` and `PAYMENT_STATUS`** (`order.types.ts`), never a string literal — closed sets with one home, and visibility turns on the first. `PAYMENT_STATUS` was undeclared until 2026-09-24 despite Invariant 2 turning on it, so `"paid"` was written as a literal in the one place allowed to write it at all.
- **A shop sees the buyer as name, city and pincode** (`shop-parcel.types.ts`, order-fulfilment D7, Q22). Every org read goes through `adminOrderRepository.listShopOrders`/`getShopOrder`, which trims `Order.address` with `toShopBuyer`; the whole address never reaches an org page, API or email.
- **Order lookup returns a projection.** An order carries a customer's name, phone, email, and full address; a lookup reachable without authentication must not return them. The console's detail read is the worked example: `adminOrderRepository.getOrderById` returns the declared `AdminOrderDetail`, and `Order.address` — a `Json` column, so `unknown` whatever a cast claims — is read field by field through `toAddressSnapshot`.
- **One creation path.** Two paths with different behaviour is how one of them silently becomes the weaker one.
- **A check and a write that must be atomic are one statement.** Read-then-write is not a check, even inside `$transaction` ([ADR-0007](../../docs/adr/0007-conditional-stock-decrement.md)). Enforced twice since 2026-09-24, because until then it was enforced by nothing: `tests/unit/conditional-stock.test.ts` requires the decrement to name the floor it clears *and* requires its `count === 0` to be read, and `tests/integration/order-transaction.test.ts` races two checkouts for the last unit. Deleting the condition used to pass the whole suite.
- **Write the rows of a set in one statement, not one per row.** Every statement inside the order transaction is a billed operation *and* is held while the guarded stock decrement's row locks are, so a `for` loop of `create` calls costs checkout contention as well as money — a six-line order was 28 statements and is 18. `createManyAndReturn` where the ids are needed, `createMany` where they are not. **Key the returned ids off each row's own fields, never its position:** nothing may depend on the driver returning rows in the order they were sent, and a parcel line that resolves to no order item throws rather than writing a null foreign key. `tests/integration/order-transaction.test.ts` asserts the linkage per line by identity.
- **An order's status after payment is a summary of its parcels** (`parcel-summary.ts`, [order-fulfilment](../../docs/specs/own-store/order-fulfilment/) D4). A parcel moves only through `fulfilment.service.ts`'s `moveParcel`: one transaction that locks the order row, moves the parcel through shipping's single writer, and writes the summary with `orderRepository.syncSummary`. Lock order is Order, Shipment, Promotion, stock, ledger, as `expireAndRestock` takes them. What a move earns runs in `parcel-moved.ts`, only for the move that won: the admin's "ready to book" notice, the booked and picked-up emails (U2, U3). The shop's "ready" is `markParcelReady`; the hourly nudges and the admin's not-packed list are `fulfilment-nudges.ts` (scheduled in `fulfilment.jobs.ts`). The admin's hand booking, date change, "Mark picked up" and the shop's label link are `fulfilment-booking.ts` (D11, D7); the queue it is pressed from is `pickup-queue.ts`, and every reader's timeline is `parcel-timeline.ts` (D5). `buyer-contact.ts` resolves the buyer's email for a parcel notice. A courier webhook's update is `courier-update.ts` (D10): it moves the parcel through `moveParcel`, takes a differing ETD, and sends what cannot apply to shipping's conflict list — decided from what the locked move found, never from a read before it. The delivered and ETA emails come from `parcel-moved.ts` (U4). A cancel is `fulfilment-cancel.ts`'s `cancelParcel` (D12), one command behind the buyer's, shop's and admin's routes: scoped first (another shop's parcel, another buyer's order, a guest order are not-found), then `moveParcel` with `onlyFrom: CANCELLABLE_FROM[actor]`, so where each may cancel from is decided under the order lock. A cancel locks the order's offers before its restock, keeping Promotion ahead of stock as checkout and expiry take them. Shipping restocks and reverses in the move; `parcel-moved.ts` calls `cancel-give-back.ts` (Q37) for the rest — the parcel's share of each offer's budget, the coupon only when the summary has just made the whole order cancelled, the refund owed (payments) and, on the shop's own cancel, the fee (payouts) — with the arithmetic in the pure `parcel-shares.ts` (cumulative floors, capped at the captured total). `buyer-cancel-view.ts` and `shop-cancel-fees.ts` are the buyer's and the shop's reads of it.
- **Side effects belong to the transition that earns them.** A confirmation email fires from the state change, not from whichever route happened to trigger it.
- **Throw `DomainError` for anything a user should see**, `NotFoundError` / `ConflictError` as appropriate. A bare `throw new Error(...)` is treated as an internal fault and reported generically — correct for a config or code failure, wrong for "insufficient stock" ([ADR-0013](../../docs/adr/0013-one-error-envelope-and-useserverform.md)).
- **No `any` in this tree** — it sits on the money path ([`/CLAUDE.md`](../../CLAUDE.md) Invariant 4).

## Structure

`order.service.ts` holds the order transaction and owns it. Around it: `sale-gates.ts` (may this line still be bought), `basket-discounts.ts` (the bridge to the offer engine, including the coupon claim), `payment-confirmed.ts` (what happens once the money is real — ledger, recipient, confirmation email). Each exists so its domain is not a standing reason for the order service to change; that took the file from eight other domains to two ([ADR-0036](../../docs/adr/0036-a-files-reasons-to-change-are-a-decision.md)).  `sale-gates.ts` answers the one question *may this line still be bought* — bidding, archiving and org withdrawal behind a single call, placed after the stock reservation so the lock ordering is race-safe; a new reason to refuse a sale belongs there, not as a fourth `await` in the transaction. `order.repository.ts` owns the order's writes ([ADR-0003](../../docs/adr/0003-one-repository-per-aggregate.md)), and `admin.order.repository.ts` is a read model; nothing writes an order's status by hand since order-fulfilment unit 3 deleted the console's status change (Q30, Q36). `admin.order.*` are reads on the same aggregate — **not a separate admin domain**; an admin order list is a query on checkout. `reservation.ts` is what the order transaction takes from the catalogue — the priced facts, the stock on hand, and the hold itself — through catalog's `productService` and `stockService` on the caller's `tx`, so catalog is not a reason for the order service to change and `ProductStock` keeps its one writer ([ADR-0055](../../docs/adr/0055-an-admin-surface-reads-through-projections-and-writes-through-the-aggregates-one-repository.md)). `parcel-preview.service.ts` answers the checkout page's "how will this basket ship" before any order exists: it reads catalog's products through `productService` and splits them into parcels, so the allocate route reaches one domain.
