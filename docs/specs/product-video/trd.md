# TRD — product video

- **Status:** 📝 Draft
- **Domain:** catalog, checkout
- **Phase:** 6 — Catalogue richness
- **Verified:** 2026-08-13
- **References:** [spec.md](spec.md), [ADR-0003](../../adr/0003-one-repository-per-aggregate.md), [ADR-0015](../../adr/0015-mobile-first-design.md), [Invariant 4](../../../CLAUDE.md), [CONTRACTS.md](../../CONTRACTS.md), [INTEGRATIONS.md](../../INTEGRATIONS.md)

> Technical approach and decisions. No code — references to existing code only, to justify a decision.

## Approach

Two decisions carry this feature: where a video is hosted, and how media is modelled. They land in one change rather than two.

Hosting is settled against a constraint rather than a preference — see D1. The model is the part worth designing. Today a product's gallery is `Product.images String[]` plus a separate `Product.thumbnail`, which can express a list of photographs and nothing else. R2 asks for a sequence the org composes with a video anywhere in it, and an ordered heterogeneous sequence is not two arrays: two arrays need a third field to say how they interleave, and whatever component reads them inherits the job of merging them, which puts sequencing logic in a renderer.

The temptation is to add `videos` alongside `images` now and model it properly later. That buys nothing — both shapes are on the wire, so it is two `[CONTRACT]` changes and two migrations to reach the same place, and the first one is thrown away. The model change is the enabling change, so it goes first and video arrives on top of it.

## Technical decisions

- **D1 — Video is hosted on YouTube, unlisted, embedded from `youtube-nocookie.com`; not Vercel Blob.** The Hobby Blob allowance (~1 GB stored, ~10 GB transferred per month) is account-wide — separate stores do not partition it — and the same store serves every product image, category hero, and avatar. One 30-second 1080p clip is 8–15 MB against roughly 500–800 KB for every photograph on a product page combined, so video is 15–20× the bytes per view of the thing it sits next to, and a few hundred plays a day exhausts the month. Exceeding the allowance is not billed, it is **cut off for 30 days**, which takes the catalogue's images down with the video. Trading a working storefront for a nice-to-have is the wrong trade at any price. Independently, Blob is object storage: no transcoding, so a single bitrate reaches every buyer, which fails R8 and contradicts [ADR-0015](../../adr/0015-mobile-first-design.md)'s premise that the phone on a slow connection is the primary case.
- **D2 — The reference is storage-agnostic: a `kind` and a `ref`, never a URL with a provider baked into it.** If YouTube's branding or availability later forces a move to Cloudflare Stream or R2, that must be a renderer change and a backfill of `ref`, not a schema migration. D1 is a decision about a free tier, and free tiers change.
- **D3 — Media becomes a `ProductMedia` relation, not `creatives Json[]` and not a second array.** Ordering becomes a column, so R2 is expressible and enforceable (`@@unique([productId, position])`) instead of implied by array index. `Json[]` was the lighter option and is rejected: Prisma types it as `JsonValue`, so every read needs a Zod parse to recover a type, which makes our own column an untrusted boundary — [Invariant 4](../../../CLAUDE.md) exists to keep untrusted input out of the database, not to be re-run on the way out of it. It also gives up any constraint that a product has at least one photograph, and any indexable answer to "which products have video".
- **D4 — The cover choice is a flag on the media row (`ProductMedia.isThumbnail`), not a URL or a foreign key on `Product`.** Storing the org's choice as a string on `Product` is what the old `thumbnail` column did, and it is why an edited gallery used to leave a stale card image on every listing — the note on `deriveThumbnail` (`server/catalog/admin.product.service.ts:33`) records that bug. Deriving from `images[0]` was the fix; R12 reopens the choice, so the fix has to come from the shape instead of from removing the choice. A flag on the row gives three guarantees the string cannot: a **partial unique index** (`WHERE "isThumbnail"`) makes at most one cover per product a database fact rather than a convention; a row-level `CHECK (NOT "isThumbnail" OR kind = 'IMAGE')` makes R12's "never a video" a database fact too; and the cascade from `Product` takes the flag with the row, so a deleted photograph cannot leave a dangling cover. A foreign key on `Product` would get referential integrity but neither of the other two.
- **D4a — `Product.thumbnail` survives as a cache of the flagged row, and there is no fallback.** The choice lives on the flag (D4); this column holds the URL that flag currently points at, so listings, search, cart lines, and order lines keep reading one table. There is deliberately no "else the first image" branch: R15 makes exactly one flagged row an invariant, so a resolver with a fallback would be code for a state that must never exist, and a fallback is how an unset cover becomes survivable instead of loud. `deriveThumbnail` (`server/catalog/admin.product.service.ts:33`) is **deleted**, not relocated — the rule it implements is the rule R12 replaces.
- **D4b — The cache is recomputed inside the same `$transaction` as any media write, and this is the only place D7 is knowingly violated.** A derived column is a second copy of a fact. It is kept because resolving the cover through a join on every listing and search result costs a query on the store's hottest reads, and because a `NOT NULL String` is the only *database-level* guarantee that a product has a picture at all (D13). Recomputing in the transaction means nothing can commit with the two disagreeing. If media writes ever gain a second path that skips the recompute, this decision is void.
- **D4c — The invariant is exactly one flagged row per product, held at both ends.** Creation requires the flag in the payload; deletion of the flagged row is refused while it is flagged (R15, A12). Refusing the delete is the strict reading and the deliberate one: promoting another row automatically would reintroduce the derivation D4a just removed, and would do it in the one situation where the org has demonstrably not chosen. The cost is one extra step when an org wants the cover gone, paid in the UI by offering "set another as cover" in the refusal rather than by relaxing the rule. R11's separate "at least one photograph" boundary check collapses into this one — a product that must always carry a flagged `IMAGE` row cannot have zero images — so D13's image rule and this are the same check.
- **D5 — `MediaKind` is a Prisma enum, declared once, consumed by an exhaustive switch.** A closed set spelled as strings in more than one place is the failure recorded against `ProductFlag` in [CONTRACTS.md](../../CONTRACTS.md).
- **D6 — The variants are disjoint.** A photograph row and a video row share `position` and a description and nothing else; neither carries the other's fields as optionals. A union where every variant holds every other variant's nullable columns is the coupling the single list is accused of and the one thing that would earn the accusation.
- **D7 — `Product.images` is migrated into rows and dropped, not kept in parallel.** Two sources of truth for one gallery is how a product comes to have two shapes, which is [ADR-0003](../../adr/0003-one-repository-per-aggregate.md)'s reasoning applied to a column.
- **D8 — Media is part of the Product aggregate**, reached through the existing product repository. No second repository, no separate media service ([ADR-0003](../../adr/0003-one-repository-per-aggregate.md)).
- **D8a — The table is `ProductMedia`, owned by `Product`, holding `ref` directly; not a shared `Media` library.** A reusable asset table is a legitimate future shape, and it was the alternative here. It is deferred, not rejected on principle, because it separates two things this feature does not yet need separated: the **asset** (a file, a video ID — genuinely reusable) and the **placement** (this asset, at this position, in this gallery, with this description — reusable never). `position` and `description` are properties of the placement, so they cannot live on a shared row without breaking the first time an asset is reused. The relational form of "a product points at many media" is therefore a join table carrying exactly those two fields — which is this table, under this name. `ProductMedia` is the correct name in both designs: the owning table now, the join table later. `Media` is the right name for the asset table if and when one exists, and reusing it here would claim a generality that invites a second nullable owner column. Note also that the implicit many-to-many Prisma would generate cannot carry extra fields, so ordering (R2) rules that form out regardless.
- **D8b — What defers cheaply, and what a library would cost now.** The migration is the same either way: `images String[]` becomes placement rows, and extracting distinct `ref`s into an asset table later is mechanical and does not move the DTO, provided the read shape stays an ordered list of kind, ref, and description (D2). Paying for it now would buy four unasked-for costs: R10 stops being one cascade and becomes refcounting or a garbage-collection job we do not have, with orphaned blobs that cost money; a shared table on a marketplace lets one organisation's product reference another's asset unless the asset is scoped by `orgId` and every write checks it, which is a new authorization surface on a path that has none; a two-level graph is an extra round trip on the hottest read, since Prisma resolves nested `include` as additional queries by default; and R11 is harder to check across a join than against owned rows. The trigger to revisit is a second gallery — the category hero, home hero, and avatar are all single-`String` columns today, not galleries, so nothing currently shares with anything.
- **D9 — The embed is click-to-play against a derived poster; no iframe in the initial HTML.** YouTube's player is roughly 600 KB of script, and mounting it on load would regress the product page's largest-contentful-paint on the device that matters most. This is also what satisfies R5 and R6: no video, no iframe, no cost.
- **D10 — A video is added by pasting its URL, parsed to an ID at the boundary and stored as the ID.** There is no video file upload, which sidesteps the ~4.5 MB serverless request-body cap noted in [INTEGRATIONS.md](../../INTEGRATIONS.md) — the cap that already makes our 5 MB image limit unreachable in practice. Photographs continue through `server/catalog/image-upload.ts` unchanged.
- **D11 — Each row carries its own description, replacing the positional alt text** generated at `src/components/product/product-gallery.tsx:191` and `:276`. R7 is a gap this migration is already in a position to close, and it will not be cheaper later.
- **D12 — Reordering is an explicit position, saved deliberately.** Drag-and-drop alone is not an answer on a phone ([ADR-0015](../../adr/0015-mobile-first-design.md)); a move-up/move-down control on each row is, and R9 is judged at ~360px.
- **D13 — R11 is enforced in the product schema at the boundary, not by a database constraint.** "At least one child row of kind `IMAGE`" is not expressible as a column check or a unique index; it needs a trigger or a deferred constraint, and a trigger is a second place where product rules live. So the rule goes in the Zod schema under `src/lib/validation/schemas/`, which is also what gives the org the inline message A8 asks for, from the same declaration the server enforces ([ADR-0013](../../adr/0013-one-error-envelope-and-useserverform.md)). Worth stating plainly: this is an application-level guarantee, the same class as the `Category` delete check noted in [BACKLOG.md](../../BACKLOG.md), and anything writing rows outside the schema — a seed, a script, a future importer — bypasses it. The partial backstop is D4: `Product.thumbnail` is already a required non-empty column, so every product carries at least one photograph reference whatever its media rows say. R11 makes that explicit and extends it to the gallery, but the durable half of the guarantee is the column that already exists.
- **D13a — What the database does and does not hold, after D4.** The check once considered here — `CHECK (position <> 0 OR kind = 'IMAGE')`, forcing the first slot to be a photograph — is no longer wanted. It only ever mattered because the cover was defined by position, and it cost R2's video-first case. D4's flag replaces it with two constraints that are strictly better and that R16 makes exact: **at most one cover per product** (partial unique index) and **the cover is a photograph** (row-level check), with position left entirely free. What remains beyond the database's reach is "at least one flagged row" and "at most ten rows" — both are counts across rows, so neither is a row-level check nor a unique index, and both need a trigger. They stay boundary rules (D13, D16). The `NOT NULL` on `Product.thumbnail` is the backstop for the first: a product row cannot exist without a cover URL in it, whatever its media rows say.
- **D14 — Any YouTube link is accepted, from any channel, with no OAuth and no API key.** Embedding is an iframe against a video ID; nothing about it is authenticated. OAuth would only be needed for us to upload on an org member's behalf or read private metadata, and we do neither (D10). For save-time validation, YouTube's oEmbed endpoint needs no key, returns the title, and fails for a video that does not exist or is private — enough to reject a typo at the boundary. It cannot tell us the uploader has disallowed embedding, which is why R13 exists as a render-time state rather than a validation rule.
- **D14a — The consequences of accepting third-party video are accepted knowingly.** A video we do not own can be deleted, made private, age-restricted, or un-embedded at any moment, so the unavailable state (R13) is a requirement rather than an edge case. A monetised third-party video also carries YouTube's advertising into our product page, which can include a competitor's. Both were weighed and accepted: the alternative is requiring every org to own every video, which is a content-operations burden the store cannot enforce anyway.
- **D15 — The poster frame is derived from the video ID, not stored.** `i.ytimg.com/vi/<id>/hqdefault.jpg` is deterministic, so a column would only be a second copy that can go stale. This also removes the extra required form field Q3 worried about. `hqdefault.jpg` is the size to use — `maxresdefault.jpg` 404s for any video never published above 720p. `i.ytimg.com` must be added to `images.remotePatterns` in `next.config.ts` or `next/image` refuses to render it ([INTEGRATIONS.md](../../INTEGRATIONS.md)).
- **D16 — The ten-item cap (R14) is a boundary rule.** A count of child rows is not a row-level check, so this is Zod alongside D13's image rule. The existing upload control already carries a `maxImages` notion (`src/admin/image-upload.tsx:191`), so the surface exists.
- **D17 — Choosing the cover is a required action on the photograph, not a separate field.** On a phone the affordance is a "Set as cover" control on each photograph's row in the media list, with the current cover badged — the same list R9 and D12 already build, so it costs no new screen. It is required: the server rejects a product payload without a cover, so the field is validated like any other mandatory field and surfaces inline through the same schema ([ADR-0013](../../adr/0013-one-error-envelope-and-useserverform.md)). The existing control badges `images[0]` as "Thumbnail" (`src/admin/image-upload.tsx:191`); that badge becomes a button, and the label stops being a claim the server makes on the org's behalf.
- **D17a — The form does not pre-select a cover.** Pre-filling the first upload would make the payload always valid and the requirement invisible, which is the same silent-substitution failure D3 of [product-weight-and-rates](../product-weight-and-rates/trd.md) records for `weight`: a default that stands in for a missing value is what makes its absence impossible to see. The org taps once. If that proves to be friction worth removing, pre-selecting is a one-line change to the form and no change to the server.
- **D18 — The client mirror of the old derivation is deleted in the same PR as the flag.** `src/components/shared/forms/product/index.tsx:129-137` watches `images[0]` and writes `thumbnail` to keep the form agreeing with the server. Under R16 nothing derives the cover from order, so the effect is not just wrong but actively harmful — it would overwrite an explicit choice on every gallery edit. The form displays the flagged row and assigns nothing.
- **D19 — `OrderItem` gains a picture snapshot; `CartItem` does not.** The line already carries `unitPrice` as "the price as it stood at purchase, from birth" ([ADR-0004](../../adr/0004-money-as-integer-paise.md)); the picture is the same kind of fact and its absence is the inconsistency R17 closes. A cart line stays live — the schema already says why, in the comment explaining why `CartItem` cascades where `OrderItem` restricts: a cart line is a wish, not history. The snapshot is written server-side at order creation from the catalogue, never from the request body — `src/lib/validation/schemas/order.schemas.ts:82` already states that names and thumbnails are server-derived, so this persists a value that was already being computed in the right place rather than trusting a new one ([Invariant 4](../../../CLAUDE.md)).
- **D19a — The snapshot stores the URL, and this preserves the choice rather than the bytes.** Storing a `ProductMedia` id would be referentially neat and useless: the row is exactly what gets deleted when an org member removes the photograph, which is the case R17 exists for. So it is a denormalised string, immutable once written. Being honest about the limit: if the underlying file is later removed from storage the URL will 404, so what R17 guarantees is that a past order is not *re-pointed* at a newer picture — not that the old picture is permanently retrievable. A true snapshot means copying the asset under an order-owned path, which doubles storage on a tier that is already the binding constraint (D1), so it is out of scope. Order history renders a placeholder when the image fails, which it must do anyway.
- **D20 — R10's cleanup is narrowed, and this is the status quo rather than a new gap.** A snapshot needs the old asset to keep being served, while R10 wants removed media to stop being served; the two cannot both be absolute. Deleting a `ProductMedia` row deletes the record, and no stored file is deleted — which is what happens today: nothing in the codebase calls Blob's `del()`, so orphaned files already accumulate. That is now load-bearing for R17 rather than merely untidy, and it has a cost on a ~1 GB allowance (D1), so reclaiming unreferenced storage is named as out of scope in the spec instead of being left to look like an oversight.

## Packages
None. D9 is a small client component. `lite-youtube-embed` does the same job and was considered, but a dependency whose whole content is a click-to-play wrapper is one we would still have to style and make accessible ourselves.

## Data model
`[MIGRATION]` — new `ProductMedia` table (`productId`, `kind`, `ref`, `position`, `description`, `isThumbnail`, unique on `productId, position`, cascade from `Product`) and a `MediaKind` enum. Two constraints go in as raw SQL, since Prisma's schema language expresses neither: a partial unique index on `productId WHERE "isThumbnail"`, and `CHECK (NOT "isThumbnail" OR kind = 'IMAGE')` (D4). `Product.images` is backfilled into `IMAGE` rows in position order, with the row matching the product's existing `thumbnail` flagged so no org's current cover is silently reassigned by the migration; where none matches, position 0 is flagged. That "where none matches" branch exists **only in the backfill**, because every pre-existing row already satisfies `thumbnail === images[0]` and the migration must still produce exactly one flag if one does not; it is not a runtime fallback, which D4a rules out. `Product.thumbnail` keeps its column and its `NOT NULL` and is written only from the flagged row, never from input (D4a, D4b).

`OrderItem` gains a picture column, written at creation and never updated (D19). Existing lines are backfilled from their product's current cover, which is the only value available — it is not what those buyers saw, so the backfill freezes today's picture rather than recovering history. Stating that plainly matters because the column will later look like it was always authoritative. `[MIGRATION]`

## API / contract changes
Yes — `[CONTRACT]`, and now in two domains. The product DTO's `images: string[]` becomes an ordered `media` list; `ProductFormInput` (`server/catalog/admin.product.types.ts`, one declaration since PR-45) gains it and the required cover. The order line DTO's picture stops being derived and starts being read from the persisted snapshot (D19), which changes where the value comes from without changing its shape on the wire — worth flagging in [CONTRACTS.md](../../CONTRACTS.md) precisely because a same-shape change is the kind that passes review unnoticed. Storefront gallery, product card, org product form, and the admin product pages move in lockstep, and [CONTRACTS.md](../../CONTRACTS.md) updates in the same PR.

## Test plan
Per [TESTING.md](../../TESTING.md) the persistence and boundary paths are the high-coverage targets here; the embed is presentational.
- Backfill preserves order: a product's images become rows whose positions reproduce the original array.
- A saved position survives a read-back from the database, not just from the response.
- Positions stay unique and gapless across an insert, a delete, and a reorder.
- A media payload with an unrecognised `kind` is rejected at the boundary (D5).
- A pasted URL that is not a parseable video reference is rejected with a shown message ([ADR-0013](../../adr/0013-one-error-envelope-and-useserverform.md)).
- `ref` is stored as an identifier, never a full provider URL (D2).
- A product card renders `thumbnail` whatever the first media row is (R3, D4).
- A product with no media rows renders today's page, and emits no iframe (R6, D9).
- A payload whose only media is a video is rejected; the same payload with one photograph added is accepted (R11, D13).
- Removing the last photograph from a published product is rejected, while removing the last video is accepted (R11).
- The backfill leaves every existing product satisfying R11 — no row ends up with zero `IMAGE` media.
- Setting the cover updates `Product.thumbnail`, asserted by reading the product row back (R12, D4a).
- Reordering the gallery changes `position` and nothing else — the cover, `thumbnail`, and every listing are byte-identical before and after (R16, A9). This inverts today's behaviour, so it is the test most worth writing first, and `deriveThumbnail`'s existing tests are replaced by it rather than adapted.
- A product payload with no cover is rejected (R15, D17); one with a cover on a `YOUTUBE` row is rejected (R12).
- Deleting the flagged row is refused; changing the cover first and then deleting succeeds (R15, A12, D4c).
- The database refuses two flagged rows on one product, and refuses a flagged `YOUTUBE` row — asserted against the constraints, not the service, since the point of D4 is that these hold without application help.
- No sequence of add, delete, reorder, and cover change leaves a product with zero or two flagged rows (R15, D4c).
- The backfill flags the row matching each product's pre-existing `thumbnail`, so no product's card changes appearance across the migration.
- Changing a product's cover after an order exists leaves that order line's picture unchanged; a cart line's picture follows the product (R17, A14, D19).
- An order line's picture is never writable from a request body, asserted by posting one and reading back the catalogue's value ([Invariant 4](../../../CLAUDE.md), D19).
- Order history renders a placeholder for a picture that no longer resolves (D19a).
- An eleventh media item is rejected (R14, D16).
- A media row whose video no longer resolves renders the unavailable state, and its siblings still render (R13).
- Deleting a product leaves no media rows (R10).
- Design-token and mobile checks on the new gallery affordance, per `tests/unit/design-tokens.test.ts`.

## Delivery
Shipped as one change. This is a solo project with no reviewer, so slicing it into independently-reviewable increments buys nothing that its cost in half-migrated schemas is worth.

What is *not* negotiable is the order of the irreversible steps inside it, which is a deploy-safety constraint rather than a review one:
1. Add `ProductMedia`, `MediaKind`, and `OrderItem`'s picture column; backfill both from existing data. Additive only — the old columns still work at this point, so a failed deploy rolls back cleanly.
2. Cut every reader over to the new shapes.
3. Only then drop `Product.images`.

The order-picture snapshot must be live **before** any cover-changing control reaches an org member, or a cover change silently rewrites order history in the window between. Since it all ships together, that means the snapshot write goes in with the same migration, not after it.

## Decided
Closed 2026-08-13 by the product owner. Each is now carried by a decision above; recorded here so the reasoning is not lost.

- **Q1 — Whose YouTube channel?** Any channel. A link is a link, wherever the org found it. No OAuth or API key is needed for this — see D14 — and the consequences of hosting content we do not own are accepted in D14a. This closes the question that was blocking Draft → Accepted.
- **Q2 — Is an unlisted video an acceptable exposure?** Yes. Unlisted is treated as public-enough for product marketing.
- **Q3 — Who supplies the poster frame?** YouTube's, for now — derived rather than stored (D15). An org member-supplied still stays available as a later addition without a schema change.
- **Q4 — Is a per-product media count capped?** Ten items per product (R14, D16).
- **Q5 — Does R3 need enforcing in the database?** Partly, and the strongest available guarantee is deliberately declined — see D13a for the row-level check that would work and what it would cost. What remains: `thumbnail` stays `NOT NULL` as the database-level guarantee that a product has a picture, its value is derived from the first `IMAGE` row (D4), and the recompute happens inside the same transaction as any media write (D4a). "At least one image" and "at most ten" stay boundary rules, since neither is expressible without a trigger.

- **Q6 — Is there a real reuse case already?** Deferred. The shared asset library stays out of scope on D8b's terms, and the trigger to revisit is unchanged: a second gallery, or a photograph genuinely repeated across a whole category. Recorded rather than closed, because the answer can change without anyone writing code.
- **Q7 — Should an order line snapshot its picture?** Yes, and it comes into this feature rather than waiting for [order-and-cart-lines](../multi-vendor-marketplace/order-and-cart-lines/) — carried by D19, D19a, and D20. It was raised as pre-existing behaviour, but R12 turns it from latent into live: once an org member has a control that changes the cover, a completed order silently changing appearance stops being theoretical. Doing it here also avoids changing the order DTO twice, since PR 2 is already a `[CONTRACT]` change.
