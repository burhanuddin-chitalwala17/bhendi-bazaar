| Q7 | How long are delivery rows kept, and who sees them? | 13 months, then deleted by the daily `social.retention` pass (Q11). No admin screen in this subfeature; the rows are shaped so one can query them later, and failures are logged without bodies | Claude · reversible | 2026-11-06 | Enough for a year's cap and dispute look-back; DPDP holds only what is needed; was: a monthly pass, made daily to share social-selling D15's job | implemented (unit 3) |
| Q9 | Does the event row keep its audience? | Yes: `NotificationEvent` also stores `audience` (TRD D1 lists eventKey, kind, orgId, facts, createdAt), so a delivery job and the later digest know how its recipient was resolved without re-deriving it from the kind | Claude · reversible | 2026-11-25 | Found while building unit 1; parcel notices (unit 2) carry buyer and shop audiences under kinds that do not fix one | implemented (unit 1) |
| Q10 | How does the hub learn whether a badge item is still open? | Each emitting unit adds its kind's check to one registration module, `still-open.registry.ts`, whose `registerStillOpenChecks()` the bell route and the morning-email job call before reading, so no check depends on which modules a request happened to load. A kind with no check, or whose check throws, keeps its items: never hide work unasked | Claude · reversible | 2026-11-25 | TRD D3 says each kind declares `stillOpen`; found in unit 1's review that a side-effect registration is lost if nothing imports it; was: each unit calls `registerStillOpen` from a module the bell route imports | implemented (unit 3) |
| Q11 | Who builds TRD D7 (retention), which no Delivery unit owned? | Unit 3. `social.retention` is a job of its own, queued daily by `channels.maintain` beside `channels.meta-retention` (its spec in `server/shared/jobs/`, so channels never imports notifications; its handler is notifications'); it deletes `NotificationEvent` rows older than 13 months in batches of 1,000 by `createdAt`, their deliveries going by cascade. Later social-selling deletions (D15) join the same handler | Master session · reversible | 2026-11-25 | The master assigned it; queued by the daily pass rather than self-rescheduling because that pass already exists and a lost chain would need it anyway | implemented (unit 3) |
| Q12 | How is the 9 am run started, with no schedule slot? | An `emit` that writes a DIGEST row also queues `notify.digest` for the next 09:00 IST with `enqueueLater` (slot = that IST date), so an idle hub queues nothing and a lost run is re-queued by the next event. A run settles every row it covers (SENT, SKIPPED or SUPERSEDED), so a twin run that day sends nothing; Resend is keyed on (shop, member, date) | Claude · reversible | 2026-11-25 | TRD D4 said self-rescheduling with `startAfter`; a chain needs a starter and a restarter, the event that needs the email is both. Departs from D4's wording, not its outcome | implemented (unit 3) |
| Q13 | Where does an item open when its screen is not built yet? | Kinds whose screen does not exist yet (conversations, failed and held posts) open the shop's home; a connection opens Channels; a Status due opens the home too until whatsapp-status-kit ships its Status page (the at-once email keeps its own link). `kind-view.ts` holds the map; the unit that ships a screen points its kind there. Items carry no post caption, so "A post failed: <first words>" reads "A post failed" until the post's owner supplies it. Rows show an icon per kind, not per platform, and "WhatsApp needs a payment method" waits for the unit that emits it | Claude · reversible | 2026-11-25 | ux: never a dead link; facts are ids only (Q7) | implemented (unit 3) |
| Q14 | Is there a dismiss route? | No. ux.md: "every item opens the screen that fixes it and disappears once fixed: nothing to mark read by hand", so the TRD's "dismiss" route is not built; an item leaves by its owner's still-open check (Q10). A kind with three or more open items is one row with its count (ux: Many items). A list that fails to load says "Could not load what needs you. Try again.", a state ux.md lacked | Claude · reversible | 2026-11-25 | The signed-off ux wins over the TRD's gate list | implemented (unit 3) |
