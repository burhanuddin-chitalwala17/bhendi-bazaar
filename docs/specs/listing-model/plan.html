2 · Why Amazon refuses the Tote bag

Amazon's per-type rules sit hidden in its template's formatting; read out, HANDBAG asks exactly the 13 fields on your screen. Adding fields to the product fixes only part of it:

Amazon asksWhat we haveWhat fixes it
Item weight + unit · height/length/width + units · size infoStored on the product, never sent; the sender can't build "value + unit"send what we have
Outer materialOur Material goes to Amazon's material, the wrong field for bagsremap
Strap type (Adjustable, Cross-Body, Shoulder…)We ask "detachable or not": a different questionnew question
Department · Age rangeFollow from Audience (Women → Womens, Adult)derive
Number of itemsPack quantity exists, the bag type doesn't ask itadd to type
Style · Inner material · Number of pockets · CapacityNo question at allnew question

Across all ten Amazon types, plus Flipkart and Meesho, the same pattern repeats: about a third of what's missing is stored but unsent, a third is mis-mapped or derivable, and a third has no question. Meesho also needs maker, packer and importer each with an address and pincode; we hold one free-text maker and one packer-or-importer.

3 · The model you described

The Bhendi Bazaar product holds every attribute any channel we support needs. Each channel keeps its own catalogue of what it asks, refreshed only when that channel changes. Between them sits one mapping layer that says, for every channel field, where its value comes from. Adding a channel is rows; adding an attribute is a row.

What changes from today, in one line: the questions become data (an admin adds an attribute without a deploy), each channel's requirements become a stored catalogue rather than something we only learn from a refusal, and every channel field has exactly one row saying where its value comes from, so nothing is guessed and nothing is silently dropped.

Separate type models: yes, and they already half exist

You asked whether BB and each channel should have their own product types. Yes: a BB type ("bag", kind "tote") means "what we ask a shop"; an Amazon type (TOTE_BAG) means "what Amazon accepts". They are different things and must not share a table. Today the Amazon side is only a text value inside a map row; the plan gives it a real model with its fields, requirements, allowed values and units, loaded from Amazon's own definitions API and from the Flipkart and Meesho templates we already extracted.

4 · Runtime mapping: one product to one channel

Nothing channel-shaped is stored on the BB product. When a listing is checked or sent, it is built fresh from the product and the maps, then the channel's own overrides are laid on top. What was sent is kept on the channel listing.

  participant L as Channel listing
  participant A as Amazon

  loop each field
    FM->>P: source? attribute · derived · core · brand · shop · constant
    P-->>FM: value (+ unit)
    FM->>FM: value map · unit conversion · Amazon's shape
  end
  FM-->>L: payload + "missing: inner material, pockets"
  Note over L: shown to the shop before sending:
every required field, filled or not, and where it's filled
  L->>A: send (check-only first)
  A-->>L: accepted, or refused with field names
  L-->>FM: a refusal on a field with no map raises a setup request

The same build answers three questions with no extra code: can this be sent (completeness, per channel), what will be sent (the review screen), and what's still missing and who fixes it (the shop for an attribute, the admin for a map, a developer for a new attribute type).

8 · Phases

  1. 0 · Unblock the bag now (days, no model change)Send weight and measurements with units; remap Material to outer material; derive Department and Age range from Audience; ask pack quantity on bags; add Strap type, Style, Inner material, Pockets and Capacity as facts and maps; apply the shop's default brand. Your Tote bag lists.
  2. 1 · Channel catalogueNew models for channel types and channel fields, loaded from Amazon's definitions API and the extracted Flipkart and Meesho templates. Readiness reads real requirements, so "incomplete" is finally true.
  3. 2 · Field maps, one tableField map rows replace the attribute map, fill and value map split: source (attribute, derived rule, core field, brand, shop, constant), value map and unit conversion. An admin mapping screen with suggestions. Setup requests write here.
  4. 3 · Attributes as dataAttribute dictionary and type-attribute rows replace code-declared facts (one migration copies today's 28 facts and 10 measures with every product's answers). Admin attribute editor. New ADR supersedes 0052.
  5. 4 · Dynamic form + completenessThe form renders from the type's attributes, badged per channel, with per-channel completeness; brand parties (maker, packer, importer with pincode) replace the free-text fields.
  6. 5 · Retire the old pathsRemove the old fact declarations and map tables once nothing reads them; one diagram in ARCHITECTURE.md.

Each phase ships on its own and keeps every channel working. Phase 0 is a fix; phases 1 to 5 go through spec, UX sign-off and technical plan.

9 · Your decisions

1. Attributes become data an admin creates.Reverses ADR-0052 and Q32 (you chose code-declared facts two days ago). The attribute's type stays in code. Recommend: yes, it's what your vision needs.
2. The form asks the union of every supported channel.Every question shows, badged by channel; required only for channels the shop has connected. Recommend: yes.
3. Channel listings are built at runtime, not stored as a second copy.We keep the channel's overrides and what was last sent. A stored copy per channel drifts the moment the product changes. Recommend: build at runtime.
4. Product type follows its category; brand defaults to the shop's.No brand-to-category link. Recommend: yes.
