# Decisions — multi-vendor-marketplace

- **Verified:** 2026-11-25

> Carried over on 2026-11-25 from the programme's `data-model.md` (closed 2026-08-08; it did not say who decided each), when a programme parent on main came to keep spec.md and decisions.md only ([ADR-0084](../../adr/0084-main-holds-only-finished-work-planning-lives-on-its-feature-branch.md)). The diagram and the full tables: `git show 5ecf1cac:docs/specs/multi-vendor-marketplace/data-model.md`. `prisma/schema.prisma` is what exists.

| Q | Question | Answer | Decided by | Date | Why | State |
|---|---|---|---|---|---|---|
| Q1 | How do users relate to orgs? | Many-to-many through `ORG_MEMBER`, replacing the 1:1 `USER`→`SELLER`; `SELLER` is renamed `ORG` throughout; one membership per user per org (`@@unique([userId, orgId])`), `role` an attribute of it | as recorded in data-model.md | 2026-08-08 | A vendor is an organisation with people in it, not a person: a user can operate several orgs and an org can have several operators | implemented |
| Q2 | Is anything preselected (`isDefault`)? | No, nowhere. The buyer chooses a delivery address at checkout; whoever creates a product chooses its location, and that choice is a `PRODUCT_STOCK` row | as recorded in data-model.md | 2026-08-08 | Nothing is guessed on a person's behalf | implemented |
| Q3 | How is a category subtree read? | In application code: load the category table, collect descendant ids, query `categoryId: { in: [...] }`. No path column, no recursive CTE, no schema addition. `CATEGORY` is self-referencing, so depth is unlimited; `SUBCATEGORY` is dropped | as recorded in data-model.md | 2026-08-08 | A third level needs no migration; `SUBCATEGORY`'s many-to-many with `PRODUCT` was flags in disguise, which `ProductFlag` already covers | implemented |
| Q4 | How are category cycles prevented? | On the write path: walk up from the proposed parent and reject if the edited node appears (and self-parenting), as a `DomainError` on `parentId` so it lands inline (ADR-0013) | as recorded in data-model.md | 2026-08-08 | Postgres cannot forbid A→B→A declaratively | implemented |
| Q5 | What unit is `ORDER_ITEM.unitPrice`? | Integer paise from birth (ADR-0004); the boundary converts ₹1,200.50 to `120050` and back | as recorded in data-model.md | 2026-08-08 | So it is not migrated twice by money-as-paise; nobody types paise into a form | implemented |
| Q6 | Cart as rows or JSON? | `CART_ITEM` rows | as recorded in data-model.md | 2026-08-08 | More standard and consistent once everything else is relational, and the sign-in merge becomes a set operation; reverses the YAGNI position in stock-locations-and-allocation's TRD | implemented |
| Q7 | What does an order line hold? | `ORDER_ITEM`: quantity and the unit price as bought, a real FK to `PRODUCT`; `SHIPMENT_ITEM` points at it for what went into each parcel | as recorded in data-model.md | 2026-08-08 | A sold product's deletion fails loudly instead of orphaning a JSON blob, per-product revenue is a SQL question, and a split line (3 from the shop, 10 from the warehouse) stays linked to what was ordered | implemented |
| Q8 | Where does stock live? | `PRODUCT_STOCK`, the `PRODUCT`↔`ORG_ADDRESS` many-to-many; never on `PRODUCT`; the shown figure is the sum across rows | as recorded in data-model.md | 2026-08-08 | One product can be held at several pickup locations (stock-locations-and-allocation TRD D2, D3) | implemented |
| Q9 | What is `ORG_ADDRESS`? | A pickup location: courier nickname, contact name and phone, active flag | as recorded in data-model.md | 2026-08-08 | A business address and a place a courier collects from are not the same record | implemented |
| Q10 | Is an order linked to a buyer and a buyer address? | The buyer is optional (guest checkout; identified by code plus the delivery snapshot's name and phone). `deliveryAddress` is a snapshot, not a link to `BUYER_ADDRESS` | as recorded in data-model.md | 2026-08-08 | Editing an address must not rewrite where a delivered order went, as ADR-0002 keeps price on the order | implemented |
| Q11 | Which referential actions are set deliberately? | `Restrict`: `ORDER_ITEM.productId`, `PRODUCT.categoryId` (was `Cascade`), `CATEGORY.parentId`, `PRODUCT_STOCK.orgAddressId`. `Cascade`: `ORG_MEMBER.userId`/`.orgId`. Not `Cascade`: `AdminLog.adminId` | as recorded in data-model.md | 2026-08-08 | Order history, a category's products, a parent's children and a location's stock (spec R8) are not deleted from under their owners; a membership means nothing without both ends; deleting an admin must not erase their audit trail | implemented |
