> Technical approach and decisions. No code — references to existing code only, to justify a decision.

## Approach

An enhancement is a row and a job: the request is recorded in the transaction that enqueues it, the worker runs one tool through one provider, writes the proposal to the object store under a proposals prefix, and marks the row proposed. Accepting copies the proposal to its final key and registers it as a derived asset of the source through the media-library seam; discarding deletes the object. Providers sit behind one interface per capability so the choice is configuration and a bake-off, never a rewrite.

## Technical decisions

- **D1 — `Enhancement` is the ledger; the proposal is an object, not an asset.** A request names its photograph by the asset when the caller knows it — the library does — and by the URL its row carries when that is all it has, as the product editor does; never both. Accepting in a gallery hands the row the result; accepting in the library adds it beside the original and the grid re-reads, because there is no row to hand it to. Columns: org, requester, source asset, tool, preset, provider, state (`REQUESTED`, `RUNNING`, `PROPOSED`, `ACCEPTED`, `DISCARDED`, `FAILED`), proposal object key, result asset id, cost in paise, error, timestamps. The proposal lives at `proposals/<enhancement id>` until accepted, so the library never shows what nobody chose (spec R3), and a discard is one object delete. Built in PR-185 as `server/content/enhancement.repository.ts`, the one writer, with every state change a conditional statement from the state it may leave; the proposal key and the transform shape are declared once in `server/content/enhancement.types.ts`, which the browser loads too and so mirrors the Prisma enums rather than importing them.
- **D2 — Tools are a closed set, each its own pipeline.** `cutout`: provider segmentation → PNG with alpha. `white`: cutout → composited on `#FFFFFF`, padded square, with sharp. `studio`: cutout → a vertical gradient plus a soft elliptical contact shadow, with sharp. `scene`: cutout → provider scene generation from the preset's prompt → the cutout pasted back at its placement → sharp. `light`: sharp only — normalise, then a gentle output gamma, then an unsharp mask — no provider; two passes with a raw hand-off, because sharp fixes its own operation order and would run the stretch after the lift (`server/content/tools/light.ts`, PR-185). `enlarge`: a plain high-quality resize with sharp, no provider and no cost. That is a fidelity decision before it is a price one — an upscaler that reconstructs detail redraws pixels the camera never saw, which is precisely what D4 refuses to let a service do, while a resize cannot change what the product looks like and only makes the file large enough for a channel to take it. One tool per run; chaining is the member running a tool on a result (spec R1). As built (PR-191): `server/content/tools/cutout.ts` measures the product's bounds from the alpha channel rather than trusting sharp's `trim`, which reads a border off the corner pixel and has none to read on a cut-out; `white` and `studio` place that cut-out unresized on a square they size to it, so the product's pixels are the cut-out's. Every margin, gradient stop, shadow radius and blur is declared once in `server/content/tools/backdrop.ts`. A cut-out is proposed as **PNG** — flattening it to WebP would throw away the transparency that *is* the result — so the proposal's format is a table keyed by tool in `server/content/enhancement.types.ts` and the object's key carries the extension. As built (PR-198): `server/content/tools/scene.ts` runs the three steps in that order and treats what comes back as a **backdrop** — the canvas is the preset's own shape at the painted scene's resolution, capped at the stored ceiling, the painted scene is cropped to it rather than stretched, and our cut-out goes back on top at a placement we chose, because a placement the service chose is one we could not check the product against. Its margins are `backdrop.ts`'s, the same ones `white` and `studio` place against. As built (PR-193): `server/content/tools/enlarge.ts` bakes the EXIF turn in, refuses a photograph whose long side already clears the target with a `DomainError` the member reads — a proposal that changes nothing still costs a slot and still asks for a decision — and otherwise scales by the smallest *whole* factor that clears it with a lanczos3 kernel, capped at `MAX_IMAGE_EDGE` (ADR-0026), aspect derived by sharp rather than by our rounding.
- **D3 — One interface per capability, chosen by configuration.** `segment`: Cloudflare Images' `segment=foreground` on the images zone (the production images host already sits on Cloudflare DNS; free to 5,000 a month) and BiRefNet on fal (about $0.002 an image, no minimum). `scene`: Bria product-shot on fal (about $0.04; licensed data, no-training warranty). `upscale`: none. Real-ESRGAN on fal was the candidate and was dropped in PR-193 — reconstruction is refused on fidelity (D2), so `enlarge` has no capability to put behind an interface. Providers are reached with `fetch`, no SDK, so nothing outside the provider module knows a vendor. Photoroom is out of scope for its monthly floor. As built (PR-191): `server/content/providers/segment.ts` declares the interface and the one sentence an org member is ever shown when a service fails; `server/content/providers/segment/zone.ts` and `…/model.ts` implement it and are the only two files in the repository that know a vendor exists. `segmenterFor` in `server/content/providers/index.ts` takes the preference from **`IMAGE_SEGMENT_PROVIDER`** (`zone` | `model`, defaulting to `zone`), falls to the other where the preferred one is not set up, and refuses with a `DomainError` where neither is — which the request path runs before a quota slot is spent. Availability is a property of the environment, not a probe: the zone one is unavailable while the public image base is an `r2.dev` URL, which has no transforms, so local development falls through to the model; the model one is available exactly while **`IMAGE_MODEL_API_KEY`** is set, and **`IMAGE_MODEL_ENDPOINT`** moves where it sends. Every call out is bounded by a 30s `AbortSignal.timeout`. Nothing in the directory imports the catalog: a service is handed the public base and a key-to-URL function. As built (PR-198): `server/content/providers/scene.ts` declares the painting capability and the two sentences an org member can be shown, and `server/content/providers/scene/model.ts` is its one implementation — **one painter, not two, because a scene is a generation and nothing we already pay for generates**, so the seam exists for a second to arrive as a file beside it rather than as a rewrite. `scenePainterFor` has no preference to read for the same reason and refuses with a `DomainError` where the key is absent. A paint is bounded by a 60s timeout of its own, since a generation is slower than a transform, and the cut-out travels **as a data URL**: it is an intermediate nobody stored, so handing a service a link to it would mean publishing an object, deleting it afterwards and leaking one on every failure. `IMAGE_MODEL_API_KEY` and `IMAGE_MODEL_ENDPOINT` are now read in one place, `server/content/providers/model-host.ts`, since both capabilities buy from the same account.
- **D4 — Pixel identity is a test, not a hope.** For `scene`, the cutout's opaque pixels are compared to the same region of the result after paste-back with zero tolerance; the pipeline fails the run rather than proposing a product that changed (spec R4). The same test guards `white` and `studio`, and from PR-198 `scene`, which is the case it was written for. As built (PR-191): `assertProductPixelsKept` in `server/content/tools/pixel-identity.ts`, run by both tools on the composite **before it is encoded** — WebP is lossy, so comparing after it would measure the encoder and would need a tolerance, which is exactly the gap a redrawn product would hide in. Only fully opaque pixels are compared; a half-transparent fringe was blended with the backdrop by design. `tests/unit/enhancement-pixel-identity.test.ts` is mutation-style: moving one channel of one pixel by one must go red, and deleting the call from either tool must too. `tests/unit/enhancement-scene.test.ts` does the same for `scene` and adds the case the promise is about — a painter that draws its own product in the middle of the setting, whose pixels must not survive the paste-back.
- **D5 — A quota resolves through three declared layers, and the platform's two numbers are a row.** An allowance is the org's own number if it has one, else the platform's setting, else a constant in code; the daily cap has no per-org layer, so it is the setting or the constant. The order is `resolveAllowance` and `resolveDailyCap` in `server/content/enhancement.types.ts` — one tested function rather than a `??` chain retyped at each call site — and the constant exists only so a database nobody has configured still answers, never as policy. The platform's numbers live in `EnhancementSettings`, a singleton by construction: one row addressed by a constant id, read and written only by `server/content/enhancement-settings.repository.ts` (ADR-0003), so the owner changes them from admin without a deploy (spec R7). `OrgEnhancementPolicy` therefore records a **deviation** — `monthlyAllowance` is nullable and null means "whatever the platform says", and `setOrgPolicy` deletes a row that would record nothing, so no org carries a copy of the platform's number to go stale the day it changes. Use is a `count` of rows in `REQUESTED`, `RUNNING`, `PROPOSED` or `ACCEPTED` within the UTC month — a discard or a failure hands the slot back, never a counter ([media-library D7](../media-library/trd.md)) — and the cap sums `costPaise` over the UTC day of the request. The enqueue refuses when the org is paused, when it is at its resolved allowance (the refusal names that number, not the constant), or when today's platform cost has reached the resolved cap; refusals are `DomainError`s the form shows.
  **A discarded run still counts.** Use is `USAGE_STATES`, which is every state but `FAILED`: by the time a proposal exists the provider has been paid and the day's cap is that much shorter, so returning the slot on a "no" would let one org spend the platform's money without spending its own. The sheet states it before a tool is chosen (spec R3).
- **D6 — Cost is recorded per run from a declared price table**, provider × tool, in paise, at the moment the provider is called; the admin view sums it per org per month (spec R9). As built (PR-190): `listOrgUsage` groups `Enhancement` by org and state in one query, so use and spend come back together and a listing never grows a query per org. Spend counts every row in the month and use counts only the states that hold a slot — a discarded run gave its slot back but still cost what it cost.
- **D7 — The time-of-use gate is one pure function over a declared table, and the store never asks it.** `server/content/channel-rules.ts` names the channels, gives each its minimum long edge and, where it has one, its required aspect, each number carrying its source on the line; the store is present with **no** rule, because "accepts what the shop has" is a decision rather than a gap. `imageMeetsChannel({ width, height }, channel)` returns what is missing and the one tool that answers it — `ENLARGE` for a size, `WHITE` for a shape, since a square of white meets an aspect without cropping the product — and answers size first, because padding a too-small photograph leaves it too small and only one tool runs at a time (spec R1). The `enlarge` target is derived from that table as the largest edge any channel asks for, not typed at the call site. Where it may be *called* is the substance of spec R6 and no type can hold it, so `tests/unit/channel-gate.test.ts` scans the source: the storefront pages, the product write path and `src/data-access-layer/` may not name it, each area listed with the reason it is out. A size rule that starts at the moment of use and migrates inwards is how a shop ends up unable to list a photograph of a real thing.
- **D8 — The label slot is refused at the enqueue**, since the request names the slot it came from; the editor also hides the tools there (spec R5). As built: the request carries the slot and its role as the editor resolved them from the shot list, and the service refuses `label` by the shot-list constant — the client knows the role, and asking the server to resolve the category again would be a query for a fact already in hand.
- **D9 — Runs are worker jobs on the existing queue**, grouped by org for fairness (worker-foundation D3), with the provider call inside the handler and a per-run timeout; a failed run parks with its reason and is re-runnable from admin (worker-foundation R3). As built: the web app enqueues `image.enhance` from a spec (`server/content/enhancement.job.ts`) inside the request's transaction, and the worker registers the handler (`server/content/enhancement.jobs.ts`); a `DomainError` marks the row FAILED with its message, anything else is rethrown for the queue, and a row left RUNNING by a dead worker is resumed rather than skipped, which the deterministic tools and the fixed proposal key make safe. The content domain reaches the store only through narrow methods on the catalog's media-asset service — read a photo's bytes, put or delete a loose object, register a derived object — never `object-store` itself.
- **D10 — The bake-off is a script**, run by the owner: N asset ids through each provider of a capability, outputs written to a proposals folder and an HTML sheet, nothing recorded as an enhancement (spec R8, A6). As built (PR-191): `scripts/segment-bakeoff.ts`, `npm run enhance:bakeoff -- --org <orgId> [--limit 20]`. It names the shop and the count before it starts, takes that shop's newest ready photographs, runs every *available* segmenter over each, and writes the results and an `index.html` under a `bakeoff/<runId>/` prefix through the same loose-object seam the proposals use — so it writes no row and creates no asset, and the only cleanup is deleting a prefix. Each cut-out is shown twice, on mid-grey and on white, with the provider's key and the milliseconds it took; the page's URL is printed at the end.

## Packages

None new in the application: `sharp` already exists; providers are plain `fetch`. Provider credentials are environment variables named for what they hold ([ADR-0037](../../adr/0037-the-host-is-a-deployment-fact-not-an-architectural-input.md)).

## UI approach

Phone first. A slot's menu gains "Improve…", opening a sheet listing the tools with one line each and, for scene, the preset list as tiles; the label slot has no menu entry. While a run is queued the slot shows "improving…" over the photo. The result opens a compare sheet: a before/after toggle with a swipe on a phone, Accept and Discard docked at the bottom. The library offers the same menu on a photo — deferred to PR 2; PR-185 ships the slot's and the extras' Improve… only, since the library tiles have no menu yet and the slot is where a dark photo's warning is read. Quota and pause states are one line in the sheet, never a modal. Admin gained that page in PR-190: the platform's two numbers in one small form — the cap typed in rupees and sent as paise (Invariant 3) — today's spend against the cap, and a card per shop with this month's use, its spend, an allowance field that is empty while the shop follows the platform, and a pause switch with a reason. It is a server component; each form is the smallest client leaf ([ADR-0034](../../adr/0034-render-on-the-server-by-default.md)) and validates with the schema its route parses ([ADR-0013](../../adr/0013-one-error-envelope-and-useserverform.md)). Every control through the primitives ([ADR-0031](../../adr/0031-one-components-home-organised-by-domain.md)). As built (PR-198): choosing "In a scene" opens the five settings as tiles inside the same sheet rather than starting a run, each tile naming its setting and the shape it makes, with a way back to the whole list; the run begins on the tile, and everything after it — waiting, compare, Accept, Discard, and the line saying a run counts either way — is what every other tool already does.

## Data model

[MIGRATION] New `Enhancement` and `OrgEnhancementPolicy` (PR-185); `MediaAsset.transform` carries `{ tool, preset, provider, enhancementId }` on a result. PR-190 adds `EnhancementSettings` and widens `OrgEnhancementPolicy.monthlyAllowance` to nullable. All additive.

## API / contract changes

[CONTRACT] `EnhancementDto` for the portal; `POST /api/org/:orgId/enhancements` (tool, preset, source asset, slot), `POST …/:id/accept`, `POST …/:id/discard`; and the two admin routes — `PUT /api/admin/enhancements/settings` and `PUT /api/admin/enhancements/orgs/:orgId`. [CONTRACTS.md](../../CONTRACTS.md) moves in lockstep.

## Test plan

Per [TESTING.md](../../TESTING.md): unit — tool pipelines on fixture images with provider stubs (white is 255,255,255 outside the mask; light is deterministic; pixel identity fails a changed product), quota and pause refusals, cost table lookups, the enqueue in the request's transaction; integration — accept registers a derived asset and discard leaves nothing; worker — a stubbed provider round trip through the queue; a mutation test that removing the identity check goes red.

## Open questions

- Which of the two cut-out services to standardise on. The bake-off exists to answer it and nothing in the application changes either way (spec R8); until it is run the default is the free one.

*Closed:* the provider accounts — a fal key and Cloudflare Images transformations on the images zone are both in place, and the only configuration either reaches is `IMAGE_MODEL_API_KEY`, `IMAGE_MODEL_ENDPOINT` and `IMAGE_SEGMENT_PROVIDER`, each named for what it holds rather than for who sells it ([ADR-0037](../../adr/0037-the-host-is-a-deployment-fact-not-an-architectural-input.md)). And the allowance and the cap as numbers. They are settings the owner edits in admin, defaulting to 300 enhancements per org a month and ₹500 a day platform-wide (PR-190), so the first provider bill is answered by an edit rather than by a release. And, from PR-198, what a key without money buys: **a scene needs a balance on that account to *run*, and none to build, typecheck or test.** Every suite stubs `fetch`, so the request shaping, the error mapping and the whole pipeline are exercised without spending anything; an empty balance costs one failed run, which is charged to no org (`USAGE_STATES`) and shows the member a sentence naming what has to happen about it ([OPERATIONS.md](../../OPERATIONS.md)).
