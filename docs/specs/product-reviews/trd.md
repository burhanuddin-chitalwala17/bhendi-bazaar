> Technical approach and decisions. No code — references to existing code only, to justify a decision.

## Approach

Reviews are already half-built: the table, the admin list, the moderation flag and the org read-only view all exist (`server/catalog/review.repository.ts`, `server/catalog/review.service.ts`, `src/app/api/admin/reviews/`). What is missing is a buyer-facing read, a write path, and a rating that is true. So this is not a new subsystem — it is one derived aggregate, one write path, two dropped columns, and a storefront section replacing a placeholder that says in as many words that reviews are not connected (`src/components/product/reviews.tsx:13-16`).

The shape of the aggregate is the whole technical question. A product's rating stops being a column and becomes a query, reaching every tile through a request-memoised context — the same shape the offer price and the bidding lock already use, so a listing asks once for a page of products rather than once per product.

Media has its own subfeature and its own TRD, written when it is picked up ([review-media](review-media/)). Nothing here may preclude it: the write path and the review DTO are the two places that will grow, and both are new in this feature.

## Technical decisions

- **D1 — One repository keeps the aggregate.** `server/catalog/review.repository.ts` gains the storefront reads and writes; the class loses its `Admin` prefix and its admin methods keep theirs, as `admin.order.*` does in checkout. A second `storefront.review.repository.ts` is the hard block in Invariant 5 ([ADR-0003](../../adr/0003-one-repository-per-aggregate.md)) — and reviews are the aggregate most likely to grow a second writer, since three surfaces already read them.
- **D2 — `isApproved: Boolean @default(true)` stays as the published flag.** It already means exactly what R15 needs, and its default is already why a review publishes immediately — publish-on-write needs no change at all. A `withdrawnAt DateTime?` rename would read better and buy nothing: who withdrew a review and when is in the admin log already (`REVIEW_APPROVED` / `REVIEW_UNAPPROVED`, `server/catalog/review.service.ts:55-72`), and the migration would touch six files to relabel a boolean.
- **D3 — The rating is derived in one place, memoised per request.** A new `server/catalog/review-rating.ts` exports `loadRatingContext(productIds)` and `ratingFor(context, productId)`, wrapped in React `cache()` exactly as `loadBiddingLockContext` is (`server/bidding/bidding-lock.ts:29`) and `loadPriceContext` beside it. `src/data-access-layer/products.dal.ts:56-57` stops copying columns and reads the context. This is [ADR-0018](../../adr/0018-one-effective-price-function.md)'s rule applied to a second number: a read path that needs a rating and does not call this is a defect, which is what makes R6 hold across tile, lane, search result and product page.
- **D4 — R10's "latest per shopper" is reduced in TypeScript over one projection, not computed in SQL.** One query selects `{ productId, userId, rating, createdAt }` for the ids on the page where `isApproved`, newest first; the reduce keeps the first row per `(productId, userId)` for the **average**, counts every row for the **count**, and buckets every row for the **histogram**. All three numbers come out of one pass, so they cannot disagree with each other or with the list (R6). Rejected: `groupBy(['productId','userId'], _avg)`, which is one query and no reduce but averages each shopper's reviews instead of taking their most recent — a different rule than R10; and a raw `DISTINCT ON`, which would be the first `$queryRaw` in the repository (there are none today) for a catalogue where this projection is a few thousand rows at worst. In-memory resolution has precedent: the offer-price sorts already resolve and order in memory over a row cap (`src/lib/product-paging.ts:17-25`).
- **D4a — The average is per voice, the count and histogram per review, and the page says so.** A shopper with three 5★ reviews puts three bars in the histogram and one voice in the average, which is the visible seam of R8 and R10 together. The summary reads "N reviews" rather than "N ratings", because the number next to a list has to be the length of that list.
- **D5 — D4's ceiling is named and the upgrade sits behind the same two functions.** One product with thousands of published reviews makes this the most expensive query on a listing page. When that happens the replacement is a raw `DISTINCT ON` lateral or an aggregate table refreshed on write, and nothing outside `review-rating.ts` changes — which is the reason the seam exists rather than the DAL aggregating inline.
- **D6 — A review with no user is its own voice.** `Review.userId` is nullable and `SetNull` on user deletion, so latest-per-user cannot key on it; folding every null-user row into one voice would merge unrelated people and silently move a product's average when an account is deleted. These rows are history — no write path creates one — so this costs nothing going forward.
- **D7 — `isVerified` stays stored and computed at creation, and stops being an admin input.** It is removed from `UpdateReviewInput` (`server/catalog/review.types.ts:41-44`): R4 says the store awards the mark, so neither the reviewer nor an admin may set it. Stored while the rating is derived, because the two are different kinds of fact — the badge is about one review at one moment and its input (a paid order) does not change, whereas a product's rating changes whenever any review does; deriving the badge would also mean a cross-domain query per rendered row. Accepted consequence: buying *after* reviewing does not retro-badge, and re-deriving on payment is deliberately not built.
- **D8 — Catalog asks checkout the purchase question through one exported function.** `hasPurchased(userId, productIds)` on `server/checkout/order.service.ts`, applying `VISIBLE_ORDER_WHERE` and the paid state, so an abandoned or expired checkout awards no badge. Catalog reading `prisma.orderItem` itself is precisely the cross-domain read that analytics is the documented exception to; a batched call also keeps the badge off the per-row path.
- **D9 — `Product.rating` and `Product.reviewsCount` are dropped in one subtractive migration** (`prisma/schema.prisma:63-64`). Nothing writes them, so there is no backfill and no dual-read window. It is a `[CONTRACT]` change: `src/domain/product.ts:27`, `server/catalog/product.types.ts:23`, `server/catalog/admin.product.domain.types.ts:37-38`, `src/components/product/console/types.ts:42`, both product DALs and `server/catalog/admin.product.repository.ts:52`, `src/components/product/product-details.tsx:51`, the seeds (`prisma/seed/products.seed.ts`, `prisma/seed.ts:277,443`) and `tests/unit/offers-strip.test.tsx`. `server/analytics/dashboard.repository.ts:198` orders `getTopProducts` by `reviewsCount` — a placeholder ordering by a column that is always 0, so it moves to `createdAt` and stops pretending to rank. Nothing sorts or filters by rating today (`PRODUCT_SORTS`, `src/lib/product-paging.ts:26`), so no query gains a join; a sort by rating would need D5's aggregate first, which is why the spec leaves it out of scope.
- **D10 — Indexes follow the queries.** Add `@@index([productId, isApproved, createdAt])`, which serves both D4's projection and the product page's newest-first list. Drop `@@index([isApproved])` and `@@index([rating])`: a boolean and a 1–5 integer are not selective enough for the planner to use, and they cost every write. Keep `[userId]` — "my reviews" is a real query.
- **D11 — Three route handlers, each parsed and each gated.** `POST /api/products/[id]/reviews`, `PATCH` and `DELETE /api/reviews/[id]`, validating a new `src/lib/validation/schemas/review.schema.ts` (Invariant 4 — no cast, whitelisted fields, create and update symmetric) and answering through `toErrorResponse` ([ADR-0013](../../adr/0013-one-error-envelope-and-useserverform.md)). `getServerSession` is the actual gate, not a courtesy — the reasoning is already written at `src/app/api/wishlist/route.ts:12-19`. Author-only on `PATCH`/`DELETE`, tested at TESTING.md's 100% authorization bar. Never accepted: `isApproved`, `isVerified`, `userName`, `createdAt`, and the product id on an update.
- **D12 — The write route carries `withRateLimit` now, while `RATE_LIMITING_ENABLED` is false.** The helper exists and costs one call (`src/lib/rate-limit/`), so the review route joins the flag rather than needing a follow-up PR when it flips. This does not contradict the spec's out-of-scope line: R10 remains what caps influence, and the limit does nothing until the flag is real.
- **D13 — The first page of reviews is a server read; "read more" is a route handler.** `src/data-access-layer/reviews.dal.ts` supplies the product page, so reviews and the summary are in the HTML the server already sends; `GET /api/products/[id]/reviews?page=` exists only because extending in place is interaction-triggered (R3). Fetching the first page from the browser would be the round trip bought for nothing that CLAUDE.md names, and would put a spinner over data the server had.
- **D14 — Nothing caches a rating, so A8 needs no invalidation story.** The storefront is dynamic — only three routes set `revalidate` (`src/app/(admin)/admin/products/page.tsx:12`, the sitemap, one OG image) — so a withdrawal is visible on the next render everywhere. After a submission the form calls `router.refresh()` rather than splicing the new review into local state, because the list, the count, the histogram and the tile have to move together.
- **D15 — Author delete removes the row; platform withdrawal flips the flag.** R9 is a hard delete of one review (its sibling is untouched, since nothing aggregates through the author), R15/R16 is `isApproved: false` with the row intact for the admin portal. `Review.productId` keeps `onDelete: Cascade`: a review carries no money and no attribution, which is the case [ADR-0020](../../adr/0020-money-bearing-records-never-cascade.md) leaves cascading.
- **D16 — Moderation keeps going through `recordAdminAction`** after the committed write ([ADR-0021](../../adr/0021-audit-trail-never-fails-the-action.md)), which `review.service.ts` already does correctly. A buyer's own create, edit and delete are not admin actions and are not logged there.

## Packages

None. Everything here is Prisma, Zod, and hooks the repository already has.

## UI approach

`src/components/product/reviews.tsx` is replaced in place — summary, histogram, list and the write control — and stays a server component; only the form and the "read more" control are `"use client"`, pushed to the leaf. The star input, every button and every field come from `src/components/ui` primitives with variants, not raw elements ([ADR-0031](../../adr/0031-one-components-home-organised-by-domain.md)), and the histogram's bars are token colours and `rounded-field`, never a literal ([ADR-0022](../../adr/0022-design-decisions-go-through-tokens.md)). Base layout is one column at ~360px with the write control tappable and no hover-only affordance (R A2, [ADR-0015](../../adr/0015-mobile-first-design.md)). The form uses `useServerForm` (`src/hooks/core/useServerForm.ts`) against the same Zod schema the route parses, so inline validation cannot drift from the server's. R12's draft survival reuses the sign-in panel's existing intent mechanism (`src/lib/auth-intent.ts`) rather than a second draft store.

## Data model

`Review` keeps its columns; indexes change per D10. `Product` loses `rating` and `reviewsCount` (D9). No new table — review media adds one under its own TRD.

## API / contract changes

`[CONTRACT]`: the product wire shape loses `rating` and `reviewsCount` (D9), and gains nothing in their place — a rating now travels with the reviews summary, not on the product. New: the review DTO for the storefront (`id, rating, title, comment, userName, isVerified, createdAt`, no `userId`), the summary DTO (`average, count, histogram`), and the three handlers in D11. [CONTRACTS.md](../../CONTRACTS.md) records the removal and the new shapes; `hasPurchased` is a cross-domain call, recorded there too.

## Test plan

The aggregate is a pure function over rows and is tested as one, as `bidding-window.ts` is: latest-per-user wins, two reviews at the same instant resolve deterministically, withdrawn rows are excluded from all three numbers, null-user rows count separately (D6), and a product with no published reviews yields 0 rather than NaN. Authorization at 100% per [TESTING.md](../../TESTING.md): author passes, non-author refused, anonymous refused, on both `PATCH` and `DELETE`. A schema test asserts `isApproved`, `isVerified` and `userName` are rejected inbound. An integration test withdraws a review and asserts the product page, the tile and the search result all move (A8). A call-site guard test asserts every buyer-facing product read goes through `ratingFor`, in the shape ADR-0029's D3 test already established for the visibility fragment.

## Delivery (PRs)

1. **Derived rating, columns dropped** — D3, D4, D9, D10, plus the product page and tiles reading the new number. Demoable as a correct rating where 0.0 used to be.
2. **The storefront read** — summary, histogram, list, read-more, empty state (R1–R6, R3, R5), and the org/admin surfaces unchanged.
3. **The write path** — D7, D8, D11–D15, the form, and R12's sign-in hand-off.
4. **[review-media](review-media/)** — its own TRD, after these.

## Open questions

- Whether the org portal should show an org its own per-product averages. R17 does not ask for it, and the aggregate is now one call away, so it is cheap to add later.
- Whether `seo` emits `aggregateRating` once the number is real. No JSON-LD carries it today; that belongs to the [seo](../seo/) spec, and Google's rules on self-serving review markup need reading first.
- Whether a purchase made after a review should retro-badge it (D7's accepted gap). Cheapest answer, if it ever matters, is to award the badge when an order is paid rather than re-deriving on read.
