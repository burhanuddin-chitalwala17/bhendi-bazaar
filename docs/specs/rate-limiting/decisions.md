# Decisions — rate-limiting

- **Verified:** 2026-10-30

> Replace a Q in place until it is implemented (end its why with "was: …"); supersede only implemented ones ([ADR-0062](../../adr/0062-a-decision-is-replaced-until-it-is-implemented-and-superseded-after.md)).
> Owner decides money, policy, irreversible data, external commitments, taste.
> Claude decides the rest, marked `Claude · reversible`. Other documents cite Q ids.
> A budget is requests per window, per route, per caller (Q10). Policies are declared once in `src/lib/rate-limit/policies.ts`; the route → policy map is `src/lib/rate-limit/registry.ts`.

| Q | Question | Answer | Decided by | Date | Why | State |
|---|---|---|---|---|---|---|
| Q1 | When, and how wide? | Build it now, as the product-wide mechanism: one registry every public route is classified in, and every later module classifies its own routes there | Owner | 2026-10-29 | Rate limiting done once and generalised, so no module ships an unlimited endpoint by forgetting; sits in the Phase 4 hardening plan | implemented (units 1–3) |
| Q2 | `auth` — account creation, password reset and resend, password change | 5 per 15 minutes | Claude · reversible | 2026-10-29 | The budget the parked limiter already carried; a person needs one or two, a script needs thousands | implemented (unit 3) |
| Q3 | `sign-in` — the credentials sign-in | 10 per 15 minutes, per address, checked inside the credentials provider | Claude · reversible | 2026-10-29 | Typos are normal, so more than `auth`; limiting inside the provider keeps next-auth's own response shape, which its client parses | implemented (unit 3) |
| Q4 | `lookup` — guest order lookup and the email-verification link | 10 per 15 minutes | Claude · reversible | 2026-10-29 | Both answer whether a guessed secret is real; a buyer re-checking an order needs a handful | implemented (unit 3) |
| Q5 | `coupon` — the checkout quote | 20 per 15 minutes, counted only when the quote carries a code | Claude · reversible | 2026-10-29 | Guessing needs a code in the request; the quote also re-prices on every basket change, which must not use up a shopper's budget (offers-hardening Q9) | implemented (unit 3) |
| Q6 | `payment` and `order` | `payment` 10 per minute (create, verify, free-order confirm, abandon); `order` 20 per minute (order creation) | Claude · reversible | 2026-10-29 | The parked limiter's budgets; one checkout makes two or three payment calls | implemented (units 2–3) |
| Q7 | `checkout` — parcel planning, shipping rates, stock check | 60 per minute | Claude · reversible | 2026-10-29 | Unauthenticated, each one reaches a carrier or the stock; a checkout re-asks on every pincode and basket edit | implemented (unit 3) |
| Q8 | `cart`, `bid`, `message`, `account` | `cart` 100 per minute (cart and wishlist writes); `bid` 20 per minute; `message` 5 per 10 minutes (contact form); `account` 30 per minute (addresses, profile, picture, reviews, review upload tokens, shop creation) | Claude · reversible | 2026-10-29 | Cart takes the most generous budget its call sites declared (sync and clear had tighter ones; a burst of cart edits is normal), contact keeps its own; signed-in self-service writes share one ceiling | implemented (units 2–3) |
| Q9 | What is exempt? | Public reads (product list, search suggestions, a product's reviews, the signed-in user's addresses and profile, next-auth's own reads), callers that authenticate by signature (the Razorpay webhook, the marketplace consent callback), and the Shiprocket webhook | Claude · reversible | 2026-10-29 | A read shows what the pages already render; a gateway's retry refused by a limit is a payment never recorded. Shiprocket is unauthenticated, but sends every update from its own few addresses, so a per-address limit would drop real ones; its fix is a shared secret (BACKLOG watch list) | implemented (unit 2) |
| Q10 | Is a budget per policy or per route? | Per route and caller: the key is the route, then the account or address | Claude · reversible | 2026-10-29 | Ten signups must not use up the same address's password reset | implemented (unit 1) |
| Q11 | What does the boot gate refuse on? | `APP_ENV`, the store's URL and token, and the trusted address header. Checked at build (`next.config.ts`) and at boot (`src/instrumentation.ts`). The rest of `validateEnv`'s list is logged at boot, not refused, until each is checked against Vercel | Claude · reversible | 2026-10-29 | A boot-only check lets a deploy go live and fail every request (A3 says it must not go live); refusing on keys this feature did not audit could refuse a deploy for an unrelated reason | implemented (unit 1) |
| Q12 | Which header is the caller's address? | The one named in `RATE_LIMIT_CLIENT_IP_HEADER`, required when deployed (`x-vercel-forwarded-for` on Vercel). If it holds a list, the last entry, which the trusted edge added. Locally, unset means `local` | Claude · reversible | 2026-10-29 | The header is a property of the host (ADR-0037 D3); the first entry of an appended list is the caller's to choose | implemented (unit 1) |
| Q13 | Does CI exercise the shared store through a local proxy (TRD D1b)? | Later. The adapter is unit-tested against a stubbed client. A smoke test against the development store in the local `.env` could not run: its host (`eternal-ghoul-9195.upstash.io`) no longer resolves, so the store each Vercel environment points at must be checked live before merge | Claude · reversible | 2026-10-29 | No proxy could be run here to prove the CI wiring, and unproven CI config is worse than none | parked |
| Q14 | Does an outage raise an alert (R5, A4)? | Later: a logged error now, an alert when error-tracking lands | Claude · reversible | 2026-10-29 | Alerting is error-tracking's mechanism (Phase 5) | parked |
| Q15 | Are admin and org portal handlers limited? | Later; they are outside the registry's scope | Claude · reversible | 2026-10-29 | Behind an authenticated, audited gate | parked |
| Q16 | How is a route named in the registry? | `"<METHOD> /api/<path>"`, the path as the folder spells it (`[id]` kept); one entry per exported method | Claude · reversible | 2026-10-29 | The gate derives the same string from the file tree, so nothing is typed twice | implemented (unit 2) |
| Q17 | What are the store's variables called? | `RATE_LIMIT_STORE_URL` and `RATE_LIMIT_STORE_TOKEN`, with `KV_REST_API_URL` and `KV_REST_API_TOKEN` read as a fallback for one release | Claude · reversible | 2026-10-29 | Named for what they hold (TRD D8, ADR-0037 D4); the fallback means the integration's existing values keep working | implemented (unit 1) |
| Q18 | What does a refused sign-in show? | The refusal's own "try again in N minutes" message, in place of the generic sign-in failure | Claude · reversible | 2026-10-29 | R6: a refusal says when to retry; "wrong email or password" would send the user round again | implemented (unit 3) |
| Q19 | Do preview and production share budgets if they share a store? | No: every key is prefixed `ratelimit:<APP_ENV>:<policy>` | Claude · reversible | 2026-10-30 | A preview test burst would otherwise use up production buyers' budgets, and the reverse | implemented (review fixes) |
| Q20 | How long does a request wait on a slow store? | 1000 ms, then it is allowed (D3) and logged once per policy per window | Claude · reversible | 2026-10-30 | Upstash's default of about 5 s adds that latency to every limited call while the store is slow, and allows silently; a log per request would flood | implemented (review fixes) |
| Q21 | Is sign-in capped per account as well as per address? | Later: sign-in is limited per address only, so an account attacked from many addresses has no per-account cap | Claude · reversible | 2026-10-30 | Revisit with account lockout, which needs its own unlock path | parked |
