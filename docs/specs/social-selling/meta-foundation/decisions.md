| Q1 | What happens when an account removes our app inside Instagram or Meta, or a person asks Meta to delete their data? | Removal: Meta's deauthorize notice turns the connection Needs reconnecting at once, with the daily check as a backstop. Deletion: we delete that person's credentials and details from every connection holding them, answer Meta with a status link and confirmation code, and a public page shows the request's status by its code | Claude · reversible | 2026-11-22 | Meta's review requires both callbacks; both concern every connection, so they live here. Moved from connect-instagram Q10 | decided |
| Q2 | How long are Meta's raw events kept? | 30 days, then deleted; what each event caused (a message, a comment) is kept by the tool that owns it, under its own retention | Owner | 2026-11-22 | Long enough to prove each event was handled once and to debug a fault; no longer, since events carry personal data | decided |
| Q3 | How do events reach the tools: one queue job per event, or facts handed on by the drain? | By the drain: one queue job per connection reads stored events in order and hands neutral facts to the sinks the owning domains register (ADR-0078). One job per event would cost a queue row per comment in a burst and lose per-conversation order | Claude · reversible | 2026-11-23 | Same decoupling and same "no tool sees a payload" as R4 asked, at a fraction of the queue rows | implemented (unit 3) |
| Q4 | How are signatures checked while Meta's app secret is rotated? | Under the current secret or, while `*_PREVIOUS` is set, the previous one; the intake counts matches on the previous so it can be removed when they stop (TRD D12) | Claude · reversible | 2026-11-23 | Answers the spec's rotation hazard without dropping events signed during the change | implemented (unit 1) |
| Q5 | Which secret signs and proves Instagram Login calls? | Instagram API with Instagram Login has its own app id and secret (`META_INSTAGRAM_APP_ID`, `META_INSTAGRAM_APP_SECRET`); its token exchange and its webhook signatures use them. `appsecret_proof` is added only to Facebook Graph calls, signed with the Meta app secret; the spike confirms whether Instagram's host accepts a proof under the Instagram secret | Claude · reversible | 2026-11-23 | The fresh-context review of unit 1: one secret for both would sign Instagram calls with the wrong key | implemented (unit 1) |
| Q6 | One error class per failure, or one carrying a code? | One `MetaError` carrying our `SOCIAL_ERROR` code (plus Meta's numeric code and a retry-after), and `MetaShapeError` for a read we cannot parse. Callers branch on the code, the closed set the UI already maps | Claude · reversible | 2026-11-23 | A closed set compared by constant (ADR-0003 D5) instead of five near-identical classes; amends the architecture TRD A-D4's naming | implemented (unit 1) |
| Q7 | How do deletion and removal behave at the edges? | (a) The person's id is kept sealed only until every domain has forgotten them, then blanked; the hash stays (keyed with the secret current at the request, used for nothing yet). (b) The status page says done only when every registered `Forgetter` succeeded **and** 30 days have passed, when retention has removed the raw events they may appear in. (c) A removal notice changes a connection only if it is newer than the connection's last connect (Meta's `issued_at` where it gives one), so one handed on late never undoes a reconnect. (d) A request still pending after a day is re-queued by unit 5's daily sweep. (e) Deferred: the "connection needs you" notification is notifications-core's (not built yet); the Connect card for an open platform is connect-instagram's and connect-whatsapp's, which read `isSocialOpen`. (f) The port is `Forgetter.forget(platform, platformUserId)`, which TRD D7 called `forgetPerson(platformId)` | Claude · reversible | 2026-11-24 | The fresh-context review of unit 4: a sealed id kept after the deletion still names the person; "done" before the raw events go would be untrue; a delayed notice could disconnect a shop that had just reconnected | implemented (unit 4) |
