# ADR-0038: Background work runs on an owned worker against a Postgres job queue

- **Date:** 2026-09-25
- **Status:** Accepted

## Context

The listing programme adds work that cannot finish inside a request. An AI image enhancement is a third-party call of three to sixty seconds followed by two writes. A vision pass over a gallery is ten of those. An Instagram publish is a create, wait, check, publish sequence. Marketplace sync is paginated and slow. Every earlier deferred need in this store was designed away rather than queued — bidding derives its state at read time ([ADR-0023](0023-bidding-status-stores-only-what-the-clock-cannot-decide.md)), an abandoned checkout releases on the buyer's own action with a daily cron as backstop — and that was right for those features. It is not available here: the work is real, slow, external, and must survive the browser closing.

A spike on 2026-09-25 compared the hosted options (Inngest, Trigger.dev, Upstash QStash and Workflow, Vercel Workflows). Every one that keeps the code on Vercel does so by calling a route handler back over HTTP, so each step inherits the function's five-minute ceiling and a multi-step task has to be cut into HTTP-sized pieces. The same day produced [ADR-0037](0037-the-host-is-a-deployment-fact-not-an-architectural-input.md): the host may constrain operations, never design. The programme also needs a record of every job for a per-organisation usage quota and an activity log, so a job row in our own database exists whichever queue is chosen. Two independent pressures point at the same shape: the queue is a table we own, and the thing that works it is a process we own.

## Decision

1. **The queue is a table in the application's Postgres, managed by pg-boss.** Its schema is applied through the project's migrations like any other table ([ADR-0014](0014-deploys-run-their-own-migrations.md)), never by the library at runtime. The library is reached only through one seam, `server/shared/jobs/`, which exposes enqueue and handler registration in neutral terms. Nothing else imports it.
2. **A job is enqueued inside the transaction that writes the business row it belongs to**, through pg-boss's Prisma adapter. A rolled-back order, asset or draft leaves no orphan job, and a committed job always has its row. The job id is stored on the application's own ledger row, which records cost and outcome; the two are one fact in two tables.
3. **Jobs are executed by a long-running worker: a second entrypoint in this repository, `worker/`, that imports each domain's public surface and calls it as a function.** No HTTP sits between the queue and the code. Handlers live in the domain that owns the work (`server/content/`, `server/social/`, and so on); the worker's entry file only registers them, and is declared here as a composition root permitted to reach every domain ([ADR-0036](0036-a-files-reasons-to-change-are-a-decision.md)), as the route tree already is. `server/` continuing not to import from `src/` is what makes this entrypoint possible.
4. **Delivery is at least once, so every handler is idempotent on its job id.** The ledger row's status transition is the guard; a redelivered job finds the row already past the step and does nothing. The worker itself holds no state: everything it knows is in Postgres or R2, and killing it loses time, never data.
5. **The worker runs as a Docker container on a virtual machine the project administers, provisioned from a script kept in the repository**, so a lost machine is rebuilt in minutes. The compose file must run unchanged on any Linux host, and no host's name, API or variable appears in application code ([ADR-0037](0037-the-host-is-a-deployment-fact-not-an-architectural-input.md) D1, D4, D6). Which machine that currently is — an Oracle Cloud Always Free instance on a Pay As You Go account with a budget alert — is a deployment fact and lives in [OPERATIONS.md](../OPERATIONS.md), together with the idle-reclaim rule it must respect.
6. **There are two workers, production and staging, each on its own database**, deployed by the same GitHub Actions pipeline that deploys the site. The environment is named by the application's own variable, not inferred from the host. Each worker writes a heartbeat the admin surface reads, so "the worker has not been seen for forty minutes" is a visible fact rather than a mystery.
7. **Concurrency is limited per organisation at the queue**, using pg-boss groups, so one seller's bulk upload cannot starve another or blow through a provider's rate limit. Schedules that today live in the Vercel cron move into the worker once it runs; the cron is retired only after the worker's schedule has been observed firing.
8. **The worker's database connections and its query volume are budgeted, not defaulted.** Prisma Postgres reserves most of the direct-connection allowance for itself and meters every query as a billed operation, with a monthly allowance that, when exhausted, has blocked this store once already ([INTEGRATIONS.md](../INTEGRATIONS.md)). A polling queue at library defaults would spend that allowance in days. So the TRD sets, against those two numbers: the pool size; notify-driven wake-up with a long backstop poll rather than a short timer; one queue with one poll loop, job types distinguished inside the job; waits inside the handler rather than as delayed jobs; the heartbeat cadence; the staging worker running only while someone is testing; and the site moving to the pooled connection string so the worker's direct connections do not compete with it.

## Alternatives considered

- **A hosted queue that calls back into Vercel** — QStash, Inngest, Vercel Workflows. The conventional serverless answer and by far the cheapest to start: QStash would cost about fourteen cents a month at the programme's volume. Rejected because every step is bounded by the function ceiling and a multi-step task must be shaped around HTTP, which is a plan limit constraining design in exactly the way ADR-0037 forbids; because the job state lives with a vendor while the ledger needs it here anyway; and, for Inngest specifically, because its free tier is described by Inngest as not for production and the first paid tier is $99 a month for a store with one seller.
- **A managed worker — Trigger.dev.** The same architecture as chosen, with the vendor running the worker: no timeout, no machine to own, cheap at this size. Rejected for now because job state and code shape become the vendor's, secrets including the database URL are duplicated to the vendor, and a second deploy has to stay in step with ours. It remains the fallback if administering a machine proves more costly than expected; the handlers would move unchanged.
- **Graphile Worker instead of pg-boss.** Also Postgres-backed, MIT, with a SQL enqueue function callable from any transaction. Rejected because its per-key control is strictly serial where the programme needs "two at a time per organisation"; because it deletes completed jobs, leaving no history; because it has no dead-letter queue and no per-job timeout; and because it shipped no stable release between April 2024 and June 2026 while pg-boss shipped dozens. Both are single-maintainer projects, which is a shared risk and one reason the library is confined to a seam.
- **A Redis-backed queue — BullMQ on the Upstash Redis already provisioned.** Rejected because it puts job state in a second datastore the ledger would duplicate, cannot enqueue in the same transaction as the business row, and serverless Redis is billed per command, which a polling worker pays for around the clock.
- **A managed container host instead of a self-administered VM** — Northflank's free tier, Koyeb, Fly.io, Railway, Render. Zero maintenance for nothing to seven dollars a month. Rejected on growth and on the owner's stated wish to own the infrastructure: on a managed host every further service (a staging worker, a search index, a metrics stack) is another line item, while one free machine with twelve gigabytes runs them all. The Docker image is identical either way, so this is the reversible half of the decision and Northflank is the first stop if the machine is given up.
- **Keep designing deferred work away.** Correct for bidding and abandonment, and still the first question to ask of any new feature. Not available when the work is genuinely slow and belongs to someone else's API.

## Consequences

✅ A long-running or multi-step task is a plain function with loops and sleeps. The Instagram publish sequence is one handler, not four HTTP hops.

✅ A job and the row it acts on are written in one transaction, and the job row is the audit log and the usage meter. There is no reconciliation between "what we asked for" and "what the queue knows".

✅ A worker outage delays jobs and never loses them, and the heartbeat makes the outage visible from the admin page before anyone reports it.

✅ Every slow feature to come — marketplace sync, bulk imports, reports, schedules more frequent than daily — has a home with no ceiling. The daily-cron limit of the Vercel plan stops shaping anything.

✅ Local development needs nothing new: the queue is the same Postgres the app already uses, and the worker runs beside `next dev`.

⚠️ A second deployable. Operating-system updates, Docker, SSH, secrets in two places, database connections from two processes. About a day to set up and an hour or two a month after; the time is real and lands on one person.

⚠️ The free machine is a commercial arrangement. Oracle reclaims Always Free instances that stay idle, and a mostly-waiting worker is idle by its definition. The Pay As You Go upgrade and the rebuild script are the mitigations; per ADR-0037 D6, nothing may be correct only because the machine is free.

⚠️ The worker's idle chatter is billed. Every "anything for me?" is an operation against a metered allowance the storefront also draws on, and the direct-connection cap is shared too. Tuned as decision 8 requires, a worker costs roughly a quarter of the free allowance including its real work; at defaults it would cost seven times the whole allowance. If the storefront's own usage leaves too little room, the answer is the next database plan, not a looser worker.

⚠️ The site and the worker can briefly run different versions after a deploy. A handler must tolerate the previous release's job payload for one release, and a payload shape is a contract.

⚠️ The queue's schema sits beside Prisma's in the same database. Prisma Migrate is believed to ignore schemas it is not told about, but this was inferred rather than found stated; the TRD proves it before the first migration lands.
