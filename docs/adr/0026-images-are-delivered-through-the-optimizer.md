# ADR-0026: Images are stored small and delivered through the optimizer

- **Date:** 2026-09-16
- **Status:** Accepted — decisions 3 and 4 amended by [ADR-0027](0027-zoomable-surfaces-declare-the-size-they-zoom-to.md) (stored ceiling is 2048px, and a zoomable surface deliberately overstates `sizes`)
- **Context:** The Vercel account exhausted the free tier's 10 GB monthly Blob **Data Transfer** allowance before launch. On that tier the allowance is not billed past its limit, it is withdrawn — so the failure mode is every product image on the storefront going blank, which is the same hazard [ADR-0017](0017-video-is-embedded-not-hosted.md) named when it refused to host video in Blob. That ADR governed what we put *into* Blob. Nothing governed how it came back out.

  Three independent causes, none of which changed how anything looked:

  1. `src/components/shared/product-card.tsx` — the most-rendered component on the storefront — used a raw `<img>` from commit `2d3027b`. A listing shows twelve tiles at ~105px on a phone (ADR-0016), each fetching a full-size original: roughly 7 MB of image for 120 KB of visible pixels.
  2. `unoptimized` was added to the product gallery and lightbox in `1b844b2` and `4e3f301`. Those commits read as someone fixing a broken or quota-limited *optimizer*, and the fix worked on screen — but it moved the cost onto Blob egress, a different meter on a different page of the dashboard. **None of the five props carried a comment saying why**, so the trade was never recorded and could not be reviewed.
  3. `server/catalog/image-upload.ts` stored whatever was uploaded, up to `MAX_IMAGE_BYTES` (5 MB), with no resize and no re-encode. `Product.thumbnail` is a URL to one of those full-size rows, not a derivative. This multiplied both causes above.

  The deeper cause is that the repository enforces the conventions it has written down. `tests/unit/design-tokens.test.ts` fails the build over a `text-[0.7rem]` literal; nothing failed over a raw `<img>` on a Blob URL, a change with far larger operational consequence. Image delivery had never been named as a convention, so it was never checked.
- **Decision:**
  1. **Every image in `src/` is rendered through `next/image`.** A raw `<img>` is permitted only for a local `blob:`/`data:` preview (which costs no egress and which `next/image` cannot take) or where a renderer does not support it — `ImageResponse` goes through Satori, which knows a subset of HTML. Each exception is allowlisted in `tests/unit/image-delivery.test.ts` **with its reason**.
  2. **`unoptimized` is never used on a Blob URL.** It is allowed only for a third party's already-sized asset — `i.ytimg.com` poster frames — where optimizing spends a transformation to save bytes that are not ours anyway.
  3. **`fill` always comes with `sizes`.** Without it `sizes` resolves to `100vw`, so a 64px avatar downloads the width of the viewport. This is the same overrun as a raw `<img>` in `next/image`'s clothing, which is why it is a separate enforced rule rather than a style note. The product tile's value is declared once as `PRODUCT_TILE_SIZES` next to the tile and shared with the wishlist grid.
  4. **Photographs are downscaled and re-encoded before they reach Blob** — longest edge `MAX_IMAGE_EDGE` (1600px), WebP at `IMAGE_QUALITY`. What is stored is what is billed on every fetch, so the ceiling belongs at the write, not at each read.
  5. **Both upload paths enforce that budget, and the budget is declared once.** `MAX_IMAGE_EDGE` and `IMAGE_QUALITY` live in `server/catalog/media.ts`, the module both sides already import, because the bulk wizard uploads browser-to-Blob directly (to dodge the 4.5 MB function body cap, bulk-catalog-upload D10) and no server code ever sees those files. The server path normalises with sharp; the browser path normalises on a canvas in `src/lib/image/downscale.ts`. A budget one path enforced and the other did not would be no budget.
  6. **`images.minimumCacheTTL` is stated in `next.config.ts`, not defaulted.** `buildImagePath` timestamps every Blob path, so a URL's bytes never change and a long TTL can never serve something stale.
  7. **`tests/unit/image-delivery.test.ts` enforces 1–3 and 6**, in the manner of the design-token suite: a build-time failure with the offending file named, and an allowlist whose entries must still contain what they excuse.
- **Alternatives considered:**
  - *Upgrade to Pro and change nothing* — the conventional answer, and the one the dashboard suggests. Rejected because the overrun scales with traffic: 100 GB is 10× the runway on a leak that grows with every visitor, and Pro **bills** overage, so the failure mode changes from blank images to an unbounded invoice. It also buys nothing for page weight, which is the same defect seen from the buyer's side — a phone on a slow connection downloading 7 MB to see twelve thumbnails.
  - *Resize on upload only, and leave the raw `<img>` tags* — rejected as a partial fix that hides itself. It caps the worst case at ~150 KB per tile, which is enough to get off the cap, and then every future `<img>` looks harmless. The delivery rule is what makes the next mistake visible.
  - *Convert the components only, and keep storing originals* — rejected for the opposite reason. It fixes today's bandwidth completely, but the optimizer becomes the only thing standing between a 5 MB original and the browser, and one `unoptimized` or one missed `sizes` reopens the whole leak. Decisions 1–3 and 4 cover each other.
  - *Generate derivatives at upload and store a `thumbnailUrl` alongside the original* — the pre-optimizer way, and genuinely considered. Rejected because it doubles what Blob stores (against a 1 GB storage allowance), needs a schema change and a backfill, and picks the breakpoints at write time — where the optimizer picks them per request from the `sizes` the slot actually declares. Decision 4 keeps one file per image and lets the optimizer derive.
  - *A lint rule (`@next/next/no-img-element`) instead of a test* — rejected because the repo already has that rule and the leak happened anyway: every offending site carried an `eslint-disable-next-line`, which is a comment that silences the warning without recording a reason. The test's allowlist demands a reason, and its honesty check deletes the entry when the exemption stops being needed.
- **Consequences:**
  - ✅ A listing page's images drop from roughly 7 MB to ~120 KB, and a product page's from ~3 MB to ~60 KB. At 10,000 monthly page views the modelled Blob egress falls from ~55 GB to well under 1 GB, most of it served from the edge cache rather than the store.
  - ✅ The storefront gets materially faster on a phone, which was the real cost being paid all along and did not show up on any meter.
  - ✅ A stored photograph is now ~150 KB rather than up to 5 MB, so the 1 GB storage allowance stretches roughly thirty times further, and a missed delivery rule costs a fraction of what it used to.
  - ✅ EXIF orientation is applied at upload (`rotate()`), so a phone photograph no longer arrives sideways — previously it depended on the browser honouring metadata that the re-encode now bakes in.
  - ⚠️ Uploads are slower and more CPU-bound: the server route decodes and re-encodes every file, and the bulk wizard does the same work in the browser before each upload. A large bulk run is visibly slower than it was.
  - ⚠️ **Existing images in Blob are still originals.** This ADR changes what is written and how it is read; it does not rewrite history. The optimizer means they no longer cost full size to *serve*, so this is a storage cost and not a transfer one, and a backfill is deliberately not part of this change.
  - ⚠️ sharp is now a declared dependency rather than a transitive one of Next. It ships a platform binary, which is a real build-time cost and a real deployment constraint — the upload routes must stay on the Node.js runtime and can never move to Edge.
  - ⚠️ Every image the browser renders now passes through the image optimizer, which has its own quota on the free tier. The transformation count is bounded by (distinct images × distinct sizes) and cached for a month by decision 6, but it is a second meter to watch, and the first place to look if images break again.
