# ADR-0024: A phone number is contact data, not an identity key

- **Date:** 2026-09-12
- **Status:** Accepted
- **Context:** `User.mobile` has been unique since the first auth migration, which made a phone number a second identity key alongside email without anyone deciding that it should be one. [international-phone](../specs/international-phone/trd.md) then leaned on that index: normalising to E.164 was partly justified by making the uniqueness check compare one spelling rather than two.

  A phone number does not identify a person the way an email address does. One number is routinely shared — a household where a parent's phone is the only one, a shop where the counter number is the contact for everyone who works there, a buyer ordering on behalf of a relative who has no phone at all. Each of those is a separate account with its own cart, orders and addresses, and each has a legitimate reason to give the same number as the one we should ring about a delivery.

  Under a unique index, the second of those accounts cannot be created. Worse, the failure arrives as "this mobile number is already registered to another account" against a number the person genuinely holds, with no route forward: they cannot prove ownership to take it back, and the account holding it may be one they know nothing about. The `phone_numbers_e164` backfill had already met the same wall from the other side — it had to skip normalising any user whose `+91` spelling was taken, leaving those rows outside E.164 rather than failing the deploy.
- **Decision:**
  1. **`User.mobile` carries no unique constraint and no index.** The `User_mobile_key` index is dropped rather than relaxed: after this change nothing performs an exact lookup on a mobile, and the admin user search is a `contains` scan a btree cannot serve anyway.
  2. **Email is the sole identity key for an account**, and stays `@unique`. Credential sign-in resolves a user by email (`src/lib/auth-config.ts`) and always did, so no authentication path depends on phone uniqueness.
  3. **No code resolves a user from a phone number.** A query shaped `where: { mobile }` intended to find *the* account for a number is a defect — the answer is a set, possibly empty, possibly large.
  4. **Signup and profile updates never reject a phone for being taken.** They still validate that it is a real number through `server/shared/phone.ts`; format is checked, ownership is not.
  5. **Phone-based authentication is out of reach until a separate decision gives it an anchor.** OTP-to-sign-in, "recover my account by phone", and merging duplicate accounts by number all assume one number names one account, and that assumption is now false by design. Any such feature must disambiguate — by asking which account, or by pairing the number with something else — and needs its own ADR.
  6. **This applies to the account record only.** `UserAddress.phone`, `OrgAddress.contactPhone`, `Org.phone` and `Bid.guestPhone` were never unique and are unaffected; the E.164 storage rule from international-phone stands everywhere, unchanged.
- **Alternatives considered:**
  - *Keep the unique index* — the conventional answer, what most storefronts do, and what the schema has said since the beginning. Rejected because it encodes a claim about the world that is false: a phone number is held by a device and a household, not by an account. The cost lands entirely on legitimate users, who meet a refusal they cannot act on, while providing no real protection — anyone wanting a second account supplies a second number, or none at all, since `mobile` is optional.
  - *Keep it unique but let a new account "claim" a number from an old one* — rejected as the worst of both. It needs an ownership proof we do not have (no OTP), and a wrong answer silently moves a delivery contact off someone else's account. Uniqueness that can be transferred without verification is not uniqueness.
  - *Warn on a duplicate but allow it* — rejected because there is nothing for the user to do with the warning. Sharing a number is the expected case here, not a suspicious one, so the message would be noise on a normal action, and noise on a normal action is how people learn to dismiss warnings that matter.
  - *Make phone the login credential and drop the shared-number requirement* — the other coherent design, and a common one in Indian e-commerce. Rejected because it is a different product: it needs OTP delivery, an SMS provider, rate limiting on send, and a session story for a number that changes hands. It also contradicts the requirement that prompted this — if a number signs in, a number cannot be shared.
  - *Partial unique index over verified numbers only* — rejected as premature. There is no verification flow to key it on; it would be a constraint over an empty condition, waiting for a feature that decision 5 already says needs its own design.
- **Consequences:**
  - ✅ A household, a shop counter or a carer's phone can back as many accounts as the people using it need, which is the behaviour that was asked for.
  - ✅ Signup and profile editing lose a rejection nobody could resolve, and signup loses an `as any` on a hand-built `OR` clause at an auth boundary.
  - ✅ The E.164 backfill can finish. The rows `phone_numbers_e164` skipped only existed because of this index, and the migration completes them.
  - ⚠️ A phone number no longer narrows a support enquiry to one account. Anyone reading orders by phone gets a list and must pick using something else — order code, email, address.
  - ⚠️ Phone-based sign-in and account recovery are now blocked on a design decision rather than merely unbuilt. This is the real cost of the change, and decision 5 states it so that it is met deliberately rather than discovered halfway through building OTP login.
  - ⚠️ One person can hold unlimited accounts with one number, so phone is no longer any kind of signal against duplicate or throwaway accounts. It was a weak signal — `mobile` is optional, so an abuser simply omits it — but it is now none at all, and any future abuse control must rest on something else.
