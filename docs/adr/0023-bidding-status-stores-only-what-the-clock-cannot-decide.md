# ADR-0023: Bidding status stores only what the clock cannot decide

- **Date:** 2026-09-09
- **Status:** Accepted
- **Context:** A timed auction has states a person chooses — cancelled, sold, unsold — and states only the clock chooses: not started, running, finished. Storing both kinds in one column reads as the obvious design, and it is the one every scheduler-shaped answer assumes. It also means a row can be wrong: an event whose end time passed a minute ago is finished in fact and running in the database until something runs.

  Two forces made that unaffordable here. This project's Vercel plan cannot run a cron at minute granularity at all, so "something runs" would have had to be a request-triggered sweep — correctness resting on traffic. And the same question is asked from many places at once: the public bidding page, the product page, listings, the cart, the order transaction, the org console, the admin console. Each of those would need to agree about whether an event had ended, and any one of them reading a stale column is a product that can be bought while it is being auctioned.

  The related fact — whether an item is suspended from normal sale — has the same shape one layer out. It is a consequence of the event set, not a property of the product, and writing it onto `Product` would make it a second place the truth lives.
- **Decision:**
  1. **`BiddingStatus` is `OPEN | CANCELLED | SOLD | UNSOLD` — only what the clock cannot decide.** Whether an open event is scheduled, running, or finished is derived on every read from `startAt`/`endAt` against a clock passed in as an argument, by `biddingPhase` in `server/bidding/bidding-window.ts`.
  2. **Nothing in this feature runs on a schedule.** An event ends because its end time passed, observed whenever it is next looked at. No correctness may rest on a job having run, and nothing is cached beyond a request, so no read can be stale.
  3. **`bidding-window.ts` is pure and free of Prisma.** Phase derivation and bid arithmetic take their inputs as arguments, including the clock, so the rules are testable and reusable without a database.
  4. **Purchase suspension is derived too, and nothing is written to `Product` when an event opens or closes.** Locked means `status = OPEN` **and** either the end time is still ahead or at least one bid exists (`suspendsPurchase`), so an event that expires with nobody bidding releases the item with no cleanup step.
  5. **Derived-at-read is enforced at two strengths.** Display surfaces read a per-request memoised set of locked product ids (`loadBiddingLockContext`), which is stale by definition and only shapes what is shown; the authoritative refusal is `assertNotUnderBidding` inside the order transaction, after the stock reservation has taken the row lock. Add-to-cart checks as well, to fail early with a good message.
  6. **`status` alone never means "biddable".** A read path that needs to know goes through `bidding-window.ts` or the lock context, never a bare status comparison.
- **Alternatives considered:**
  - *Store the full state and flip it with a scheduled job* — the textbook answer, and the one a reader will expect. Rejected on the plan before it was rejected on design: Hobby offers daily cron, and an auction that ends "sometime today" is not an auction. Beyond the plan, it makes every consumer's correctness depend on a job having run, and the failure is silent and directional — the item stays biddable *and* stays suspended, which is the worst pair of the four.
  - *Flip the status lazily, on read* — the sweep without the scheduler. Rejected because it turns the public bidding page, which is the most-read route in the feature and reachable by anyone with the link, into a write path; because two readers arriving at the closing instant contend to perform the same transition; and because it buys nothing — the value being written is derivable from the row already in hand, so the write only creates the opportunity to be wrong.
  - *Denormalise the lock onto `Product` (a `biddingLocked` flag or a status value), maintained when an event opens and closes* — rejected as two sources of truth for one fact, which [Invariant 5](../../CLAUDE.md) exists to prevent. It would also need the cleanup that decision 4 avoids, for the expire-with-no-bids case that no request causes; and `bidding` would be writing into `catalog`'s aggregate to do it.
  - *Let each caller derive it as needed* — no shared module, since the arithmetic is two comparisons. Rejected because that is exactly how `ProductFlag` came to be declared three times and drift. Two comparisons repeated in nine places is nine chances to compare against the device's clock, or to forget that an unsettled event with bids still holds the item.
  - *Keep the stored status and treat it as advisory, re-deriving only at the purchase gate* — rejected as the worst of both: the column still goes stale and still needs the job, while every display surface now disagrees with the gate.
- **Consequences:**
  - ✅ No scheduled job, no queue, no sweep — the feature has no moving part that can fail to run, and it works on a plan that cannot schedule anything useful.
  - ✅ No cache invalidation to get wrong, because nothing is cached past the request that read it.
  - ✅ The rules are a pure function, so the seventeen phase-and-arithmetic tests need no database and the concurrency tests can be about Postgres alone.
  - ✅ An event that expires with no bids costs nothing to clean up: it stops suspending the item the moment its end time passes.
  - ⚠️ **Every read path that needs the answer must ask for it.** One that reads `status` and infers is a defect, and the compiler cannot see it. This is the standing cost, and it is why the rule is in the root [CLAUDE.md](../../CLAUDE.md) index rather than only here.
  - ⚠️ The display set is stale by construction, so the order transaction re-checking is not belt-and-braces — it is the only enforcement. Removing it because "the cart already checks" would reopen the race.
  - ⚠️ Listing pages pay one small indexed query per request for the lock set. Deliberate, and the shape `loadPriceContext` already established.
  - ⚠️ Phase cannot be filtered in SQL by status alone: "finished but unsettled" is a timestamp predicate, so queries and indexes carry the window rather than a single equality.
  - ⚠️ The partial unique index that makes one live event per product a database fact keys on `status = OPEN`, which the clock never clears. An event that has ended and not been settled therefore still blocks a new event on that product — correct, since the platform is mid-sale, but it means a forgotten unsettled event is a block that only an outcome or a cancellation removes.
