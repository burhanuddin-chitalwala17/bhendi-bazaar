# ADR-0015: The UI is designed mobile-first; desktop is the enhancement

- **Date:** 2026-08-09
- **Status:** Accepted
- **Context:** Bhendi Bazaar is an e-commerce store, and the majority of buyers arrive on phones. A 2026-08-09 audit of the whole app found the opposite assumption baked in wherever a layout had been judged by eye on a desktop viewport: the navbar hid search, categories, and sign-in below `md` with **no mobile replacement**, so a phone visitor had no discovery path and no way to log in; the checkout address modal had no `max-h`/scroll, so its Save button was unreachable on a phone — a returning customer without a saved address could not complete checkout at all; the product gallery set `touch-action: pan-x` on the largest element of the page, trapping vertical scroll under a thumb; the admin portal kept a fixed 256px sidebar that left ~118px of content on a 375px screen; and the most-used controls (cart quantity stepper, remove, share) were 16–32px tap targets against a 44px guideline.

  None of these were flagged by any existing gate. `tsc`, the token test, and the form-error test are all blind to layout, and desktop-first breakage is invisible in a desktop browser — which is where the code is written. The failures were also all the *same* failure: base styles written for a wide screen, with small screens treated as the special case to patch (or forget).
- **Decision:** Base styles target a ~360–390px phone; breakpoints (`sm:`, `md:`, `lg:`) **add** width, columns, and hover affordances. Concretely:
  1. **The base layout is single-column.** A `grid-cols-N`/multi-column flex row exists only behind a breakpoint prefix. Wide content (tables, code) scrolls inside its own `overflow-x-auto`; the page never scrolls horizontally.
  2. **No capability is removed on mobile.** `hidden md:flex` on a primary action (search, sign-in, nav) requires an equivalent mobile affordance in the same change — a drawer, a second row, an icon. Hiding *decoration* is fine; hiding a *path* is not.
  3. **Hover is an enhancement, never the only affordance.** `group-hover`/`hover:` revealing a control must pair with a visible-by-default (or touch-reachable) state below `md`.
  4. **Touch targets are ≥40px** (`h-10`, `size-10`, or padding that reaches it) for primary controls; nothing interactive below `size-9`. Destructive controls don't sit within 8px of frequent-use controls.
  5. **Overlays scroll.** Anything `fixed` and centred carries `max-h-[*dvh]` (dvh, not vh — the iOS URL bar) and `overflow-y-auto`, in the primitive where possible (`DialogContent` does this once for every dialog).
  6. **Inputs stay ≥16px on mobile.** `Input`'s `text-base md:text-sm` is the iOS-zoom guard; overriding an input to `text-xs`/`text-sm` at base reintroduces zoom-and-strand. Purpose-built keyboards (`type`/`inputMode`) and `autoComplete` tokens on every address/identity field.
  7. **DOM order is the mobile reading order.** Stacked grids render in source order, so what a buyer must see before acting (the bill before Place Order) must precede it in the DOM, with grid placement handling desktop.
- **Alternatives considered:**
  - ***Desktop-first with mobile overrides*** — the conventional way dashboards get built, and what the codebase implicitly did. Rejected because the failure mode is silent: the developer's own viewport always looks right, and every forgotten override ships as mobile breakage. Mobile-first inverts the default so the *desktop* polish is the part that degrades visibly during development — the failure lands on the screen the developer is looking at.
  - *A separate mobile experience* (adaptive components, `m.` routes, user-agent branching) — maximal control per form factor. Rejected as two UIs to keep correct for a solo project, and the store's pages have no desktop-only complexity that would justify it.
  - *Judgement per page* ("the admin is desktop software") — tempting for the portals. Rejected: the org portal is used by sellers who check orders from their phones, and the audit showed "desktop software" is exactly the assumption that made both portals unusable at 375px. Admin keeps the same rules with one relaxation: dense tables satisfy rule 1 by scrolling inside `overflow-x-auto` rather than reflowing.
  - *A visual-regression gate* (Playwright screenshots at 360px) — would catch what review misses. Not rejected, deferred: worth its own change once flows stabilise; a convention plus review check is what is affordable today.
- **Consequences:**
  - ✅ The default outcome of writing a component with no breakpoint prefixes at all is a working phone layout — correctness for the majority device is the path of least resistance.
  - ✅ Review has a mechanical tell: a bare `grid-cols-N`, a `hidden md:` on an action, an `h-7` on a button are each visible in a diff hunk without running anything. `/bb-review` checks them.
  - ⚠️ Desktop layouts now cost explicit breakpoint work; a page written lazily is phone-shaped on a 27" monitor. That is the intended direction of the trade.
  - ⚠️ Nothing *enforces* this — it is a convention plus review, not a test. The token test's approach (grep the classes) can't judge layout intent, so drift is caught at review or by a future screenshot gate.
  - ⚠️ "≥40px" and "no capability removed" require judgement at the margins (dense admin tables, tertiary links); the review check is a prompt to argue it, not a hard block.
