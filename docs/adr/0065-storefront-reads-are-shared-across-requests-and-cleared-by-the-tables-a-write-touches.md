# ADR-0065: Storefront reads are shared across requests, and cleared by the tables a write touches

- **Date:** 2026-11-04
- **Status:** Accepted
- **Context:** The database meters every statement, and the store was spending about 15,000 a day. Each statement was already lean (`tests/integration/db-ops-budget.test.ts`), but nothing was kept between requests: every page view ran its reads again, 5–9 statements, a missing product included, so a crawler walking the catalogue cost as much as a shopper. Four of those statements were the same on every page: the offers in force (three) and the auction locks (one). They were memoised per request only, by ADR-0018 decision 3, because a cache outliving an offer's start or end would advertise a price checkout refuses. The owner asked on 2026-11-04 for page views to stop costing this, without trading away correctness.
- **Decision:**
  1. **Display reads may be shared across requests; money never is.** A read is shared through `cachedRead` (`server/shared/read-cache.ts`), a seam that reads straight from the database unless the web server installs Next's data cache (`src/lib/storefront-cache.ts`, from `src/instrumentation.ts`). The worker, scripts and tests read live. Checkout, cart and payment keep `loadPriceContext` and every live reader (Invariants 1, 2).
  2. **The clock stays per request.** What is shared is data that does not change with time: offers not yet ended (`listNotEnded`), open auctions with their end and bid count. Which have started, and which still hold, is decided at the request's own instant (`loadDisplayPriceContext`, `loadDisplayBiddingLockContext`). This keeps ADR-0018 decision 3's guarantee — no price shown past a boundary — without its per-request query. A list chosen *by* being on offer is read live, since its membership moves with the clock.
  3. **A cached read declares every table it reads, and a write clears by table.** The prisma client reports every statement (`noteStatement`); a write to a table some cached read declares (`CACHED_TABLES`) clears the tag `table:<name>` with `expire: 0`, so the next view waits for fresh data rather than being served the old. A write to any other table (a cart, a session, a job) clears nothing. The clear is made twice: at the statement, and again after the response through `after()`, because the statement runs before its transaction commits and a page rendered in between would otherwise re-cache the old row with a newer stamp; a route handler answers only after awaiting its transaction. `tests/integration/read-cache-tables.test.ts` runs each cached read alone and fails on a table it touches but did not declare, and `cachedRead` refuses a table missing from `CACHED_TABLES`.
  4. **Every entry has an age limit**, because a write outside a Next request clears nothing: the worker's (a marketplace sale moving stock, a finished video), or a write during a page render. Next's own `revalidate` does not bound age — it serves an expired entry and refreshes it behind the response — so each entry carries when it was read, and one past its limit is read live. Product rows, which carry stock, are limited to five minutes; offers, categories, auctions, ratings, reviews and banners to an hour. Stock shown stale within that window is display only: the conditional decrement refuses an oversell (Invariant 6).
  5. **Only what a visitor cannot multiply is shared.** A list is shared only as a first page of at most 48 rows that is not a search and not chosen by offer; a review page only as page 1 from the product page; a product only by a slug of sane length. A search, a later page or an arbitrary id is read live, so request input cannot fill the cache with entries.
  6. **`unstable_cache`, not `"use cache"`.** In this version `"use cache"` needs Cache Components, which changes how every page renders, and keeps its entries in each serverless instance's memory unless a paid remote handler is configured; `unstable_cache` is shared across instances and deploys on Vercel today.
- **Alternatives considered:**
  - *Redis (Upstash) in front of the reads* — rejected for now. Every command is billed, it is a second store to keep in step with the first, and the data cache Vercel already provides does the same job with no new service. It remains the step if the store ever leaves Vercel (ADR-0037: a self-hosted Next needs a cache handler).
  - *Cache whole pages (ISR)* — rejected. The storefront chrome reads the session, so pages are dynamic; caching the data under them gets the saving without splitting every page around the session.
  - *A hand-kept map from table to tag* — rejected. It fails silently when a feature adds a table, which is the failure the table test exists to catch.
  - *Clear on commit instead of on statement* — not available through the client's events; the second clear after the response stands in. One gap remains: two requests writing the same table at once share one waiting clear, so the later one's commit may land after it. A page rendered in that window can show the old row until its age limit.
- **Consequences:**
  - A repeat view of a category, product or missing product costs no statements; the home page and the offers page cost one (the live offer list), and a search two (its rows and their ratings, read live by decision 5). Any write to a cached table — an order moving stock, an edit — clears every entry that read it, so between orders the savings hold and at an order they reset.
  - `Address` is a cached table because a product row carries its shop's pincode; a buyer saving an address therefore clears product rows too.
  - Supersedes, for display reads only, ADR-0018 decision 3; checkout's pricing is unchanged.
  - `prisma.ts` now always emits its query event, to report writes; logging it still needs `PRISMA_LOG_QUERIES=1`.
  - Vercel's data cache has its own included usage; it is read on every storefront view.
