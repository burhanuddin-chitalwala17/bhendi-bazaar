- **Verified:** 2026-11-01
- **Covers:** `src/app/*/`, `server/*/`, `prisma/schema.prisma`, `src/lib/rate-limit/**`

Describes what **exists now**, at HLD level. Not a plan — planned work is in [BACKLOG.md](BACKLOG.md) and [specs/](specs/). Update *after* a structural change, never before ([../CLAUDE.md](../CLAUDE.md) Golden Rules). Domain-internal detail belongs in `<domain>/CLAUDE.md`, co-located with the code.

## Shape

A single Next.js 16 application — one deployable, one database. Not a service architecture: the domains in [../CLAUDE.md](../CLAUDE.md) are bounded contexts inside one process, enforced by convention rather than by network boundaries.

```
Browser ──▶ Next.js 16 (App Router, React 19)      ──▶ PostgreSQL (Prisma 7 + adapter-pg)
            ├── (main)  storefront    13 pages     ──▶ Cloudflare R2   (images and video — ADR-0028, ADR-0039)
            ├── (admin) console       38 pages     ──▶ Razorpay         (payments)
            ├── (org)   seller portal 28 pages     ──▶ Shiprocket       (shipping rates)
            ├── (auth)  sign-in flow   4 pages     ──▶ Resend           (email)
            └── api/                  154 handlers  ──▶ YouTube          (embedded video; hosted video plays natively from R2)
```

Deployed on Vercel; every route is server-rendered on demand. There is no static generation and no ISR.

A second entrypoint, `worker/main.ts`, runs the job queue: a pg-boss schema in the same Postgres, reached through one seam (`server/shared/jobs/`), worked by a long-running process that imports each domain's handlers and calls them as functions ([ADR-0038](adr/0038-background-work-runs-on-an-owned-worker-against-a-postgres-job-queue.md)). The site enqueues inside its own transactions; the worker writes a heartbeat the admin dashboard reads. Its image is `infra/worker/Dockerfile`, its machine is provisioned by `infra/worker/provision.sh`, and both are deployment facts recorded in [OPERATIONS.md](OPERATIONS.md), not in code ([ADR-0037](adr/0037-the-host-is-a-deployment-fact-not-an-architectural-input.md)).

Images and video each have a delivery layer of their own. For images: uploads are downscaled and re-encoded before they reach the object store (`server/catalog/image-upload.ts` server-side, `src/lib/image/downscale.ts` for the browser-direct bulk path), and every render goes through `next/image` so the bytes served match the slot. Every write, delete and URL derivation goes through one seam, `server/catalog/object-store.ts`, so reads never pass through our code ([ADR-0028](adr/0028-images-live-in-cloudflare-r2.md)). Both ceilings predate R2 and were set because Vercel Blob's transfer allowance was withdrawn rather than billed ([ADR-0026](adr/0026-images-are-delivered-through-the-optimizer.md)). Video takes the other shape: the browser uploads the file as it is and the worker makes what plays from it — the sized renditions and a poster frame — through `server/catalog/video-transcode.ts`, chosen at the tap by `src/lib/video-renditions.ts` ([ADR-0039](adr/0039-video-is-stored-in-our-object-store-and-transcoded-by-the-worker.md)). A `<video>` draws its bytes under the policy's `media-src`, which is a different directive from the `img-src` the poster beside it uses.

## Layers

`src/` is organised by **layer** — it is a Next.js app, and the framework dictates that shape. `server/` is organised by **domain**, one directory per bounded context owning its own service, repository, and types ([ADR-0012](adr/0012-modules-are-vertical-slices-by-domain.md)).

| Layer | Lives in | Responsibility |
|---|---|---|
| Pages / components | `src/app/**`, `src/components/<domain>/**` | Rendering, user interaction ([ADR-0031](adr/0031-one-components-home-organised-by-domain.md)) |
| API clients | `src/components/<domain>/*ApiClient.ts` | The browser's only requests to our routes, through `apiRequest` (`src/lib/api-client.ts`); called from hooks, never from a component ([ADR-0048](adr/0048-a-component-renders-a-hook-holds-state-an-api-client-makes-the-call.md)) |
| Server data access | `src/data-access-layer/**` | Server-component reads, called directly from pages |
| Route handlers | `src/app/api/**` | HTTP boundary: parse, authorize, delegate |
| **Domains** | `server/<domain>/` | Business logic, transactions, and Prisma access for their own aggregates |

Two entry paths into data, by rendering mode: server components read through `src/data-access-layer/`, while client components call a hook, which calls an API client, which calls a route handler. Both converge on the same domain services.

Domains are `catalog`, `cart`, `checkout`, `payments`, `shipping`, `identity`, `notifications`, `analytics`, `promotions`, `payouts`, `bidding`, `wishlist`, `content` (what is made from an image: enhancement, renditions, capture rules, and what each channel asks of a photograph — reading catalog's assets through catalog's public surface), `channels` (a shop's authorised marketplace connections: consent, encrypted tokens, renewal and a daily health check, with each marketplace behind `providers/<name>/`; tokens never leave it — [server/channels/CLAUDE.md](../server/channels/CLAUDE.md)), plus `shared` for what genuinely spans them. Each owns its aggregate's repository ([ADR-0003](adr/0003-one-repository-per-aggregate.md)). External systems sit behind an interface in `<domain>/providers/<name>/`. Admin-facing reads are `admin.*` files inside the owning domain — there is no separate admin tree.

`bidding` is the only domain whose stored state deliberately answers less than the question asked of it: an event's status records whether it was cancelled or settled, and *when* it is — scheduled, running, finished — is derived from its timestamps against the clock on every read. Nothing in the feature runs on a schedule as a result, and no read can be stale, because nothing was cached to go stale. See [server/bidding/CLAUDE.md](../server/bidding/CLAUDE.md).

`catalog` now derives one number the same way, for the same reason: a product's rating and review count are computed from its published reviews on every read (`server/catalog/review-rating.ts`), memoised per request so a listing asks once for a page of tiles rather than once per tile. The two columns that used to hold them were written by nothing, so every product advertised itself as unrated however many reviews it carried — a stored aggregate with no writer is worse than no aggregate ([product-reviews](specs/product-reviews/) R6a).

No route handler reaches Prisma, and no service writes through a transaction client: every write is a command on the aggregate's one repository, `admin.*` modules are read models, and `tests/unit/one-repository.test.ts` scans every file under `src/` and `server/` to hold it ([ADR-0055](adr/0055-an-admin-surface-reads-through-projections-and-writes-through-the-aggregates-one-repository.md)).

## Cross-cutting

- **Auth** — NextAuth v4, JWT session strategy, credentials + Google OAuth. `src/lib/auth-config.ts` defines providers and callbacks, including a `signIn` callback that links a Google login to a pre-existing email-matched user by inserting an `Account` row — behaviour `PrismaAdapter` does not provide under a JWT strategy. `src/lib/admin-auth.ts` exposes `requireSession()` and `requirePlatformAdmin()`; `src/lib/org-auth.ts` exposes `requireOrgMember()` for server components and the `withOrg()` wrapper that every `/api/org/[orgId]/*` handler is built from, so being authorised and being scoped to one org are the same act. Signing in on the storefront happens in one sheet mounted by `AuthSheetProvider` (`src/context/AuthSheetContext.tsx`) and opened with `useAuthSheet().open({ view, reason, intent })`. It renders the same form components (`src/components/auth/`) as the `(auth)` pages, stays on the page, and finishes a named intent afterwards — carried through the Google round trip in `sessionStorage` (`src/lib/auth-intent.ts`). The pages honour `callbackUrl` only as a same-origin path (`src/lib/safe-callback-url.ts`). `src/middleware.ts` guards admin *pages*; its matcher excludes `/api`, so API authorization is in-handler.
- **Validation and errors** — Zod schemas in `src/lib/validation/schemas/` are the single definition of an accepted payload: a route parses with one, and the matching form uses the same one as its resolver. Failures return the envelope in [CONTRACTS.md](CONTRACTS.md) via `toErrorResponse`, and `useServerForm` routes field-attributed errors onto their inputs ([ADR-0013](adr/0013-one-error-envelope-and-useserverform.md)). Most route handlers return failures through `toErrorResponse`; a few still build their own body (tracked in [BACKLOG.md](BACKLOG.md)). Form-side conversion to `useServerForm` is still partial and tracked in [BACKLOG.md](BACKLOG.md).
- **Cart state** — Zustand store (`src/store/cartStore.ts`) with localStorage persistence, synced to the `Cart` table for signed-in users via `src/hooks/cart/useCartSync.ts`, which must be mounted exactly once above the router. On sign-in the local cart wins on quantity conflicts, items whose product no longer exists are dropped, and price and thumbnail are refreshed from the database.
- **Rate limiting** — one seam, `src/lib/rate-limit/`. Every public route method is classified in `registry.ts` under a policy from `policies.ts` (or exempt with a reason), and a handler calls `limitRequest` with its route's key ([ADR-0063](adr/0063-every-public-route-is-classified-for-rate-limiting-in-one-registry.md)); `tests/unit/rate-limit-registry.test.ts` fails a route nobody classified. `APP_ENV` picks the backend: in-process locally, the shared Upstash store in preview and production, where `next.config.ts` and `src/instrumentation.ts` refuse to start without its configuration. A store fault fails open and is logged. The caller is the account, or the address from the header named in `RATE_LIMIT_CLIENT_IP_HEADER` ([rate-limiting](specs/rate-limiting/)).
- **Response security headers** — `src/lib/security-headers.ts` holds both halves: a per-request Content-Security-Policy built in `src/middleware.ts` around a fresh nonce, and the invariant set (HSTS, `nosniff`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`) applied in `next.config.ts` so it reaches static assets too. `script-src` carries no `'unsafe-inline'` — Next stamps the nonce onto its own inline scripts — and the gateway is admitted by name on `script-src`, `frame-src`, `form-action` and `connect-src`. `CSP_REPORT_ONLY=1` downgrades enforcement to reporting without a code change. `tests/unit/security-headers.test.ts` asserts the properties rather than the string.
- **Encryption** — AES-256-GCM, per-message random IV, under a versioned key from `CREDENTIAL_KEYS` (`server/shared/crypto.ts`); values written before versioning still decrypt from `ENCRYPTION_KEY`. Used for stored shipping-provider credentials and, with channel-connectors, marketplace tokens.
- **Email** — Resend, templates under `server/notifications/templates/`. One of them goes to the store rather than a buyer: Contact us emails a subject and message to the support inbox with the sender as Reply-To, and stores nothing ([contact-us](specs/contact-us/)). The other Contact us option, WhatsApp, is a `wa.me` link with no server side.

## Data

PostgreSQL via Prisma 7 with the `pg` driver adapter. 113 migrations; **`prisma/schema.prisma` is the authoritative schema reference** — there is no separate schema document, by design ([ADR-0009](adr/0009-docs-reference-code-never-copy-it.md)). 68 models, 21 enums. Money is integer paise ([ADR-0004](adr/0004-money-as-integer-paise.md), landed in PR-37); the only remaining `Float` columns are weights, which are not money — `Product.rating` was the other one and is gone, because a rating is now computed from the reviews rather than stored. The Prisma client is a dev-mode global singleton in `server/shared/prisma.ts`; the `pg` Pool is constructed per module evaluation.

**Several constraints live in migration SQL rather than in the schema**, because Prisma's schema language cannot express them. On `ProductMedia`: a partial unique index and a row-level `CHECK`, which together make "exactly one cover per product, and it is a photograph" a database fact rather than a convention. They are re-stated in a doc comment on the model and asserted against the migration text in `tests/unit/product-media.test.ts` — a constraint whose only home is a migration file is otherwise invisible to anyone reading the schema ([product-video](specs/product-video/) D4/D13a).

On `BiddingEvent` and `Bid` the same device carries more weight, because there the constraint *is* the concurrency design: a partial unique index on `productId` where the status is open makes "one live bidding event per product" something two simultaneous requests cannot both satisfy, and `CHECK`s pin an ordered window, positive money, a complete sale record, and a bid attributable to either an account or a named guest. Verified against a real database in `tests/integration/bidding-concurrency.test.ts` rather than against mocks — what is being tested is what Postgres does under contention, which a stub would happily fake ([bidding](specs/bidding/) D4/D6).

One table is written by a trigger rather than a repository: `ProductPriceHistory`, filled by `Product_price_history` on every insert and price change of `Product`, because a price has several writers (form, bulk sheet, marketplace import and merge, seed) and none may skip it. Catalog reads it (`lowestListPrices`) and the order transaction passes the 30-day lowest list price to the offer engine as each line's funding basis, so the platform's share of a discount is worked out on it ([offers-hardening](specs/own-store/offers-hardening/) D7, `tests/integration/funding-basis.test.ts`). A product with no history rows falls back to its current price.

## Shipping

The one pluggable subsystem. `server/shipping/domain/provider.interface.ts` defines the provider contract, `server/shipping/providers/shiprocket/` implements it, and `server/shipping/services/orchestrator.service.ts` coordinates rate quoting. Provider credentials are stored encrypted and connected through the admin console.

**Quotes are live; booking is by hand.** Quotes come from the Shiprocket provider; an admin books the courier on Shiprocket and records it (own-store Q18). A parcel moves only through checkout's `fulfilment.service.ts`, which locks the order, moves the parcel through shipping's single writer and derives the order's status from its parcels ([order-fulfilment](specs/own-store/order-fulfilment/) D2, D4). Automatic booking is [shipping-fulfilment](specs/shipping-fulfilment/).

## Testing

291 Vitest files (227 of them under `tests/unit/`), run with `npm run test:run`. The file count is asserted by `tests/unit/docs-integrity.test.ts`; a test count is not, because nothing can check it without running the suite — which is why the number this paragraph used to carry drifted 518 → 983 unnoticed. Strategy and per-layer targets are in [TESTING.md](TESTING.md). In CI (`.github/workflows/ci.yml`) `tsc --noEmit` and the test run are blocking gates; **lint is not** — it carries `continue-on-error: true` and reports 37 errors, 35 of them `no-explicit-any`. None of those is in a route handler any more: `src/app/api/**` is at zero, so the rule holds where CLAUDE.md calls it a defect. What remains is in admin pages, hooks and the shipping provider layer ([BACKLOG.md](BACKLOG.md)).

## Intentionally absent

No caching layer (no `unstable_cache`, no Redis response cache); the three `export const revalidate` declarations — `src/app/sitemap.ts`, `src/app/(admin)/admin/products/page.tsx`, `src/app/(main)/bid/[slug]/opengraph-image.tsx` — are the whole of it, and none sits on a price-bearing read ([ADR-0018](adr/0018-one-effective-price-function.md)). Retries within a request are in-process via `server/shared/retry.ts`; work too slow for a request goes to the owned worker instead ([ADR-0038](adr/0038-background-work-runs-on-an-owned-worker-against-a-postgres-job-queue.md)). No search index; product search is a `contains` match, which no btree index can serve. No structured logging or error tracking. No feature flags. No multi-currency, no i18n.
